# Operations — pricing, orders, deliveries, kitchens

Read this before touching pricing, the order lifecycle, delivery generation, quota draws, or anything that reaches a subcontractor's page.

The data-history sections matter as much as the rules: this database has been through an import, a phone-format dedup and a draw-order reconciliation, and several columns mean something different from what their name suggests.

## Pricing

- Customer-facing chatbot prompt has the current Paket Personal S price list spelled out in `src/lib/claude/prompts/system.ts`; keep this in sync with `pricing_tiers` and `price_list_image_url`.
- The price list **image** is a third copy of the same facts and drifts silently, because nothing reads it. On 2026-08-22 its custom-request cards and the prompt disagreed in both directions: the image offered a `REQUEST ALERGI` card (tanpa susu, tanpa kacang) we do not serve, and the prompt was missing `tidak ada seafood`, which we do. A lead hit the first half the same morning and the bot denied our own artwork — see "Never deny something printed on our own price list" in `BOT_RULES.md`. V4 (`menu/price-list-personal-s-1787384421668.png`) matches the prompt's five exceptions exactly: Protein (max. 1) tanpa sapi / tanpa seafood, Preferensi (max. 1) tidak pedas / tanpa nasi, Nasi (max. 1) nasi merah +Rp 5.000. Older versions stay in the `menu` bucket under their own timestamped keys — upload a new object and repoint `settings.price_list_image_url` rather than overwriting, so a bad edit is one setting change away from being undone. **When the prompt's request list changes, change the image in the same session**, and vice versa: a customer reading the image is reading a promise the model cannot see.
- Existing orders lock in `price_per_portion` at order creation time
- The inbox thread list reads the `inbox_threads` view (migration 059), which returns one row per customer holding their newest message, so every thread loads regardless of how old it is. The search box filters those loaded threads client-side, which is only correct because the list is complete — do not reintroduce a row limit on this query. See DATABASE.md for why this is a regular view and must not become a materialized one.
- Inbound WhatsApp media expires at Meta after roughly a week, so `media_id` is not a durable reference. It is a separate column, not a rewrite of `content`, because `content` holds the caption / `[Dokumen: name]` label the bot reads back as context. A failed download is logged and the message is still saved — losing the copy must never cost the customer their reply. `getInboxImageSrc` / `getInboxDocument` read `media_url` first, then a `/chat-media/` URL in `content` (that is where `scripts/backfill-chat-media.ts` put it — it rescued 15 rows on 2026-08-12; 60 were already unrecoverable), then `media_id` as the legacy fallback. Payment-proof images take an earlier branch and keep their own copy in `payment-proofs`. For the ~60 rows whose media was already gone before the rescue, the `media_id` still resolves to a 404 — the `InboxImage` component catches the image's `onError` and shows "Photo expired — no longer available from WhatsApp" instead of a broken-image icon.
- Inbox liveness comes from a Supabase realtime channel plus a 10s poll, and the poll is the guarantee — Railway's proxy drops the websocket. Anything the UI must not show stale has to be reloaded in that poll's `refresh()`, not only in a realtime handler. - The admin inbox "Review extracted order" modal now shows server-computed `price_per_portion` and `total_price` before confirmation, but those values remain server-authoritative and are recomputed again on create.
- Manual inbox extraction now reads a deeper chat window (60 messages instead of 20) and includes saved learned-context notes in the prompt, so extraction still works after later back-and-forth pushes the original order form out of the most recent messages.
- Anthropic forced-tool extraction rejects conversations that end on an assistant turn; the inbox extraction path trims trailing assistant messages before calling Sonnet so old closed threads can still be parsed.
- The inbox extracted-order review modal supports two admin confirm modes: create the `pending_payment` order only, or create it and immediately send the payment-details WhatsApp message. The shared helper defaults to sending payment info unless the caller explicitly disables it.
- Manual order extraction now normalizes `package_size` to total portions when the chat clearly states a formula like `2 porsi x 5 hari = 10 porsi`, so the review modal prices recurring multi-portion orders correctly instead of treating day-count or per-delivery portions as the package size.
## Corporate customers buy at a negotiated rate, not off the ladder

`customers.contract_price_per_portion` (migration 070) is a negotiated per-portion price. When it is set it **replaces the `pricing_tiers` lookup entirely** — `getExtractedOrderPricing(size, nasiMerah, customerId)` returns `contract × size` and never touches the ladder — and the 5-or-6 divisibility rule does not apply, because a company buys box counts, not packages. NULL means an ordinary customer, which is every customer but one.

It exists because no code path could produce PT Bintang Lautan Sejahtera's real order: 110 porsi at Rp 35.000, a rate above every tier that has ever existed. The ladder only ever goes *down* as an order grows, which is right for a personal customer and structurally wrong for a corporate contract. Before this the replay harness could only score their case as unreproducible.

Three places read it, all through `contractPrice(customerId)` in `src/lib/claude/extract-order.ts`:

- **Pricing** — `getExtractedOrderPricing` takes an optional `customerId`. The webhook create path, the pending-order amendment path and both inbox routes pass it. Add-ons still stack: what the kitchen charges extra is charged through at cost regardless of who the customer is.
- **`packageSizeMatchingPayment`** — a corporate total is `paid / rate`, not a walk of the tier list, which would always miss. A payment that does not divide evenly by the rate (a DP) tells us nothing about the size, so it returns null rather than guessing.
- **The prompt** — `buildSystemPrompt({ contractPricePerPortion })` swaps the whole "Current price list" section for a corporate one: the rate, no package sizes, no divisibility rule, and an explicit instruction never to say a total is "belum tersedia" or to offer a different number than the one asked for. The personal price list and the price-list image are never shown to them.

Set it on the Customers page ("Harga Kontrak / Porsi", blank = ordinary pricing) or with `scripts/set-contract-price.ts <name> <rate|null>`.

**Partial payment is recorded, not modelled.** `orders.amount_paid` (default 0) is what has actually landed; `total_price` stays the contracted amount. Corporate orders arrive with a DP and settle later, and the lifecycle has no room for "half paid" — `pending_payment` → `payment_proof_received` is binary. Rather than build a second payment state machine for one customer, an admin types the received figure in the Orders detail slide-over ("Sudah dibayar") and decides when the order is paid. Nothing derives it and nothing gates on it.

- Current S-only customer price thresholds (`pricing_tiers`): 5=29k, 6=29k, 10=28k, 12=28k, 20=27k, 24=27k, 40=26k, 48=26k, 60=26k, 72=26k, 120=25k, 144=25k per portion. The even sizes are the 6-day analogues of the 5-day ladder and carry the same per-portion price as the size below them.
- The only active subcontractor now delivers Saturday, so a weekly schedule runs 5 days (Senin–Jumat) or 6 days (Senin–Sabtu). The 6-day price rows on the public list are sellable again. Minggu is still closed, as are national holidays.
- **Which days those holidays are is data, not something the bot recalls: `src/lib/holidays/id.ts`** holds the 2026 SKB 3 Menteri list (17 libur nasional, 8 cuti bersama), and `describeUpcomingHolidays()` injects the next 45 days into the prompt. The prompt used to say "closed on all tanggal merah" without naming a single date, so the model had to remember mid-sentence: asked "besok bisa kirim ga kak?" on 2026-08-16 it answered "Bisa kak, besok kami tetap kirim", then wrote "17 Agustus itu Hari Kemerdekaan RI" two sentences later and reversed itself. The customer received all three stages. Most of the calendar is not recallable anyway — Idulfitri, Iduladha, Nyepi, Imlek and Waisak move with lunar calendars, the Easter-linked days move with Easter, and cuti bersama is set annually by decree. **Each line is rendered from `isClosedHoliday()`, never from `holiday.type`**, so a date in `OPEN_DESPITE_HOLIDAY` prints as `BUKA` and the prompt tells the model to treat it as an ordinary working day. It used to read the type directly, which left the generator and the sentence disagreeing: on 2026-08-24 at 16:46 WIB Veronica Catherine asked to add lunch to her Selasa 25 delivery and was told "kami tutup dan nggak ada pengiriman hari itu" while her dinner row for that date was already on the kitchen sheet — she would have received food she had just been told was not coming. Anything that answers "do we deliver on this date" reads the same function. **Every Minggu in the window is on that same list**, rendered by `upcomingSundays()` and merged in date order, and a Minggu that is also a tanggal merah is named once rather than twice. Minggu used to be a second rule the prompt carried instead — "any date not on this list is a working day (except Minggu, which is always closed)" — which left the model to work out the day of the week for every date itself. On 2026-08-29 Julie asked for 1–7 September; the bot called that seven delivery days, quoted 28 porsi at Rp 728.000, and asked her to confirm. 6 September is a Minggu, so the run is six days and 24 porsi. Nothing was written — the hallucination validator blocked the reply twice and paused the thread before `extract_order` fired — but the customer had already read the wrong number twice. A closed date the model has to derive is a closed date it will sometimes miss, so the list carries them and the prompt does no arithmetic. The 45-day window also means the section now renders through a stretch with no libur nasional at all, where it used to be omitted entirely and the model was given no closed dates for six weeks.
- **Cuti bersama is not a closure — it is an escalation.** Justin's call: whether the partner kitchens work those 8 days depends on the kitchen, so the bot must neither promise nor refuse, and calls `ask_admin_for_help`. This is the one operational-status question it is allowed to escalate. The Idulfitri run (20–24 Maret 2026) is the heavy one: two libur nasional plus three cuti bersama.
- **The list ends at `HOLIDAYS_KNOWN_THROUGH` (2026-12-31) and must be extended each year.** The following year's SKB is normally published around September. Past that date `describeUpcomingHolidays()` returns null and the prompt tells the bot to escalate rather than treat an empty list as "no holidays coming" — but a whole year of dates silently missing is a real operational risk, so extending it is a calendar task, not a code task.
- Splitting a package's deliveries across two addresses on different days is operationally supported via the per-day address override on the daily sheet. 5 hari + 1 extra day is now simply a 6-hari package. There is still no single-portion one-off order — the smallest package is 5 portions, so an extra delivery on top of a package must draw from one the customer buys.
- Totals not on the size list but divisible by 5 or 6 are still sellable, priced at the per-portion rate of the **largest listed size below the total**, times the actual total. Examples: 15 porsi → 12's rate → 15 × 28k = Rp 420k; 25 porsi → 24's rate → 25 × 27k = Rp 675k; 50 porsi → 48's rate → 50 × 26k = Rp 1.300k. Totals that are neither on the list nor divisible by 5 or 6 must be rejected politely, **offering the nearest sellable total above and below — not the nearest list size**. Asked for 13 porsi on 2026-08-16 the bot offered 12 or 20, skipping 15: a size it prices happily when asked directly, but never volunteers as an alternative because the list is what it reads as the catalogue. That pushes a customer 7 portions past what they wanted instead of 2.
- **Never price an off-list total as repeated smaller packages.** That was the old fixed-schedule rule (15 hari = 3 × Rp 145k = Rp 435k) and it charged the small-package rate on a large order, so 25 porsi cost Rp 725k against 24 porsi's Rp 648k — Rp 77k more for one extra portion. The tier-below rule keeps per-portion price monotonically non-increasing as the order grows. This also unified the two ladders: the block rule used to apply only to fixed-schedule day counts while bebas refused anything off the list, so totals like 15 are now sellable to everyone (and cheaper than the old fixed-schedule price).
- Bulk adjust supported: `PATCH /api/settings/pricing` with `{ adjust: number }` increments all tiers at once
- Package sizes offered by the chatbot: 5, 6, 10, 12, 20, 24, 40, 48, 60, 72, 120, 144 total portions. The 6-multiples were added alongside Saturday delivery; the prices are spelled out in the "Package sizes and prices" section of `system.ts` and stored in `pricing_tiers`. Sizes off that list are priced by the tier-below rule above when divisible by 5 or 6, and refused otherwise.

## A custom/event order is tendered to the kitchens, never quoted from the ladder

An event order — one date, a large box count, no subscription — is not a package and must never be priced off `pricing_tiers`. We do not know what it costs until a kitchen bids on it, so **the quote comes from the kitchens, not from us**. The order of operations is fixed:

1. **Budget** — ask the customer's ceiling per portion and take it as a constraint, not an opening offer.
2. **Contents** — ask what they actually want in the box. An event buyer chooses the spec; a subscription customer receives the daily menu. Never assume the standard nasi + lauk + sayur + sambal.
3. **Everything else that pins the job down** — date, portion count, meal time, delivery area and address, drop-off window.
4. **Confirm the whole brief back to the customer** and get their agreement to it.
5. **Only then tender it to the subcontractors** and price the customer from the bids that come back.

**No payment request may be sent before step 4.** The bank details are composed by `createOrderFromExtraction`, so any path that creates an order also asks for money — which means creating the order early *is* asking for money early. Since 2026-08-29 the webhook passes `deferPaymentMessage: true` and sends that message after its own reply rather than from inside the tool, so the bank details land after the sentence introducing them — the composition and the rule above are unchanged, only the moment it goes out.

The rule is written from the failure. On 2026-08-25 at 08:08 a lead asked for 40 porsi makan siang in Gading Serpong for 22 September with a budget under Rp 30.000. By 08:10 — two minutes, before any price existed, before anyone had asked what should be in the box — the bot had created an order and sent BCA details with a total on it. The customer never asked for a total; they asked "minta menu nya", twice, and then "18 rb itu dapat apa saja". The bot could not answer, because Rp 18.000 was a number it had produced rather than received, and it stalled at 08:18. The thread went cold with a payment request sitting in it for a job nobody had costed.

Two things went wrong and both matter: the bot **priced an event off the personal ladder**, and it **billed before it understood the order**. A subscription package is sellable the moment a size is named, which is why `extract_order` fires early and why that is right for the ordinary path. An event is not sellable until a kitchen has bid. Treating the two the same turns a live corporate lead into an unanswerable quote.

Tendering itself is manual today — the broadcast to the kitchens is composed by hand, bids may be split across two or three of them, and the customer's selling price is never shown to a bidder. There is no tool for it and no automated path; the bot's job is to gather the brief and hand it to an admin.

## Order sizes (S / M)

- Every order has a `size` column (`text`, default `'s'`, constraint `IN ('s', 'm')`) added in migration 043. Read it through `normalizeSize()` (`src/lib/orders/size.ts`), never by comparing the raw string: legacy rows and a model-filled field both reach `null`, and anything that is not the literal `"m"` is an S order.
- **S** is the standard portion: menu items 1, 2, 3 and 5. **M** is the same nasi and lauk utama plus the fourth item on that week's menu — one extra side dish, not a bigger scoop.
- **Which kitchens cook M is per kitchen, like their delivery areas — `subcontractors.offers_size_m` (migration 078), never a literal.** Only Thenie has it today; a doc, a prompt or an `if` that names one kitchen is wrong the day a second adds the dish. The bot's prompt builds its size section from `dapurOptions[].offersM`, so it offers M for exactly the kitchens that have it and says "only size S is available" when none do.
- **What the customer pays: the S tier price plus `settings.size_m_surcharge` (Rp 4.000/porsi), on every tier.** A setting, not a constant, because it is a price. It stacks the same way the nasi merah add-on does — including on a corporate `contract_price_per_portion`, because M is a real extra dish the kitchen bills us for either way — and it is folded into `orders.price_per_portion` by `getExtractedOrderPricing(packageSize, nasiMerah, customerId, size)`, so `total_price`, the ledger and the accounting journals never learn about sizes. A missing or unparseable setting reads 0, which prices an M order as S: too cheap by 4.000/porsi is a margin an admin fixes, where a NaN would write `total_price: null` on a real order.
- **What it costs us: the kitchen's own M pair, `cost_per_portion_m` and `cost_per_portion_route1_m`** (Thenie: 24.000, both routes since migration 084). Every COGS path picks the rate through `kitchenCostPerPortion(sub, size, route)` — the dapur page, `POST /api/deliveries/daily-sheet` and the manual-order route. Each M column falls back to the *M* rate before the S one: a kitchen that quoted a single M price bills it on both routes, and reading its S route-1 rate there would cost every M portion our own courier carries at the S price.
- **A kitchen that does not cook M is never sent an M row.** `createOrderFromExtraction` re-reads `offers_size_m` after it has resolved the kitchen and downgrades to S — writing S rather than refusing, so the order still exists and the price matches the food. Its sheet would otherwise say M, it would cook S, and the customer would have paid the surcharge for a dish nobody made.
- **`resizePendingOrderFromMessage` passes the order's own size through.** Repricing an amended order without it would quietly demote an M order to S rates while the kitchen kept cooking M.
- A delivery row has **no size of its own** — it has an `order_id`, and the order has the size. Deliberately not duplicated: a size copied onto the row goes stale against the order's, the same way `order_type` went stale against the schedule.
- **The kitchen sheet at `/dapur/[id]` splits into an S tab and an M tab** for a kitchen with `offers_size_m` (`?size=s|m`, S by default), because they are two different dish lists and the cook needs the day separated, not one merged sheet with a badge per card. Each tab carries its own portion count, its own route breakdown and its own bill at that size's rates; the date picker keeps the tab. A kitchen without M sees the page exactly as before, with no tabs.
- The surcharge is stored, never derived; editing `size` on a historical order does NOT recalculate `price_per_portion` or `total_price`
- Admin can change `size` on any order via the inline select in the Orders table — calls `PATCH /api/orders` with `{ action: "update_size", id, size }`, updates only the `size` column

## Delivery

### Delivery areas

**There is no company-wide list of delivery areas. Coverage belongs to the kitchen, not to Pian Yi.** Each subcontractor row carries its own `delivery_areas` array. Those arrays **overlap in part and differ in part** — two kitchens may both serve BSD Baru while only one of them serves Karawaci — and what we can tell a customer is the union across the rows where `is_active = true`. Nothing about this lives in `settings`, and nothing about it may be hardcoded — the welcome message resolves `{{delivery_areas}}` at send time for exactly this reason.

The union is *not* stable, and coverage is not evenly deep — but **do not write today's kitchens or today's areas down here or anywhere else.** A table in a doc is a hardcode with better manners: this section held one for a day, and the eleven copies in `src/` it was describing had already drifted into two areas no kitchen serves and one served area no dropdown offered.

Read it instead. In code, `activeDeliveryAreas(db)` / `unionAreas(rows)` in `src/lib/subcontractors/areas.ts`; in the dashboard, `useDeliveryAreas()`; ad hoc, `select customer_nickname, is_active, delivery_areas from subcontractors`.

What is durable is the shape, and it is the thing to check before assuming an area is safe:

- **Some areas are served by several kitchens and some by exactly one.** The depth is per area, and it is the first thing a query tells you. An area with one kitchen behind it disappears entirely when that kitchen is deactivated or has an off-day.
- **An area disappearing is a normal consequence of a subcontractor edit, not a bug to go hunting for.** Editing `delivery_areas`, or flipping `is_active`, changes what the chatbot offers on the next message.
- **Never assign a customer to an area from a remembered list.** The candidate kitchens are those whose `delivery_areas` contain the customer's area *and* that are active — both halves queried, neither recalled.

Area names that appear in older docs are not evidence of coverage. On 2026-08-21 a Bintaro lead (`+62811811442`) asked "Gak sampai bintaro jaya ya" and the bot never answered: the docs said we served Bintaro, the live union said we did not, and nobody could tell which was true. The live union is always the one that is true.

**A place inside a served area can still be refused, and `area_neighborhoods.excluded` is how (migration 094).** The table maps cluster names to an area and the chatbot prompt renders them straight through ("**BSD Lama** neighborhoods: ..."), so an ordinary row means "this cluster belongs to that area", never "this cluster is deliverable". Coverage inside an area is not total: an area name in a kitchen's `delivery_areas` is a coarse label, and parts of it may be unreachable — Taman Tekno is a part of BSD Lama we do not reach. It was seeded as a BSD Lama neighbourhood anyway, so on 2026-08-30 the bot told Sarah Sinaga we deliver there, quoted her and sent bank details. **Deleting the row was the first answer and it was the wrong one:** deleting only stops the bot *recognising* the name, and "Area never blocks the order" then rounds an unrecognised cluster to the nearest served area and sells to it regardless. Both deleted rows are back as `excluded = true` instead — Taman Tekno (BSD Lama) and Synergy Building (Alam Sutera) — and an excluded row is three things at once: kept out of the served list the prompt renders, named in the prompt's own refusal block ("do not quote a price, do not call extract_order", escalate, never round it to a neighbour, never offer a different dapur), and checked in `createOrderFromExtraction` before the kitchen's own verdict, which withholds the order, sends no bank details and flags the thread. That last one is the load-bearing half: the prompt is guidance, the guard is enforcement. It is a global refusal, not a kitchen's — `subcontractor_neighborhoods.can_deliver = false` is the per-kitchen one and is answered by finding another kitchen. Toggle it at `/areas`. Synergy Building is refused because the building will not take a lobby drop, so the courier waits ~15 minutes for each customer to come down and the whole route behind them runs late; Naya, Cila and Winy were refunded their undelivered portions and their rows deleted on 2026-09-03 (`edit_log`, actor `system:synergy-refund`). Winy keeps her Saturday deliveries, which go to Brooklyn Apartment, not Synergy — the exclusion is the building, not the customer.

**A kitchen's exceptions inside an area live in `subcontractor_neighborhoods`, one row per kitchen × neighborhood** (migration 085, `src/lib/subcontractors/coverage.ts`). Two things a row can say, and a missing row still means "served, normal rate":

- `can_deliver = false` — that kitchen will not go there. The bot may not quote and may not call `extract_order`; `record_daily_order` books no date and tells the model to apologise and escalate. Nothing is written either way.
- `surcharge_per_delivery` — IDR **per drop, not per portion**, passed to the customer. `createOrderFromExtraction` multiplies it by the number of drops the package pays for, adds it to `total_price`, and locks both figures on the order (`delivery_surcharge_per_delivery`, `delivery_surcharge_total`) the way `price_per_portion` is locked. The payment message names it as a separate line so the total reconciles.

**Matched against the customer's address line, not their `area`/`sub_area`** — see `subcontractor_neighborhoods` in `DATABASE.md` for why those two fields cannot be trusted for this, and for the word-boundary rule that keeps "Casa Living" off "Tucasa Living".

Thenie is the worked example, from the evening of 2026-08-31: it refused Kost Casa Living outright, refused Apartemen Akasa, then re-priced Akasa at Rp 10.000 a drop when asked again an hour later (migration 086). Three customers already held paid orders at those two addresses — 65, 10 and 5 portions — with 31 delivery rows on the calendar from 1 September onwards. **A coverage rule stops the next order; it does nothing to the rows already written.** Those were deleted by hand (`edit_log`, `delete_delivery`, actor `script:hold-rows`), because the kitchen sheet keys on the date alone and would otherwise have sent a courier to an address the kitchen had refused. Whoever adds a refusal has to go looking for the rows behind it.

**In the books a surcharge is a pass-through, never revenue.** `mark_paid` splits it out of `total_price` and credits it to **2101 Unearned Delivery Fee** rather than 2100 Unearned Revenue — 2100 is only ever drawn down by `portions × price_per_portion`, so ongkir credited there would sit on the balance sheet for good. `PUT /api/deliveries/daily-sheet` then posts `Dr 2101 / Cr 2001 Accounts Payable` per meal per day, **counted in drops, not portions** (three portions to one door is one fee), because that is how the kitchen is paid and because a drop that never happens is a fee we never owe. Nothing touches 4001 or 5001: we charge Rp 10.000 and owe Rp 10.000, and a zero-margin fee on both sides of the P&L would inflate revenue and cost alike. Journal id is `ongkir_{date}_{meal_type}`, idempotent like the revenue and COGS pair beside it.

**A refund reverses the payment journal, and only what is still unearned.** `createJournalEntry({sourceType: "refund", sourceId: <order id>})` — keyed on the order, so an order can only be refunded into the books once. Pane's Rp 280.000 on 2026-09-01 is the worked example: none of her 10 porsi had been delivered (her five September rows were deleted on 2026-08-31 when she declined the Rp 10.000/drop ongkir), so the whole amount still sat in 2100 Unearned Revenue and the entry is `Dr 2100 / Cr 1002` — the exact reverse of `JV-2026-633`. **An order that has delivered portions cannot be refunded this way**: the delivered part has already moved 2100 → 4001, and reversing the full amount out of 2100 drives that account negative. Refund the unearned part against 2100 and the earned part against 4001. Nothing in the app posts a refund — no route, no button, no bot tool — so every one is a hand-written journal, and the transfer itself is manual anyway.

**An order amended after it was paid never re-posts its payment journal — book the difference by hand.** `createJournalEntry()` is idempotent on `(source_type, source_id)` and the payment journal is keyed `order_payment` + the order id, so raising `package_size` later leaves the books holding the original amount while `orders.total_price` moves. Carolin is the worked example: she paid Rp 145.000 for 5 porsi on 29 Agustus, `JV-2026-623` posted that, she added a sixth box on 31 Agustus and transferred Rp 29.000 for it, and nothing recorded the second transfer. The correction is a `manual` journal for the difference alone — `JV-2026-640`, `Dr 1002 / Cr 2100` — the same shape as Sharleen's ongkir top-up (`JV-2026-635`). Never edit the original journal and never post a second `order_payment` for the order: the first would destroy the audit trail and the second is refused by the idempotency guard. Note also that the amend wrote **no `edit_log` row**, so the only evidence of what was added is the chat.

The `/dapur/[id]` bill carries it too, as its own **Ongkir** line under each meal — `n × Rp 10.000`, counted in drops and never folded into a porsi rate, because three portions to one door is one fee and lunch plus dinner to the same door is two. We owe the kitchen the same fee we charge the customer for it, so a surcharge that is missing from this page is money we collected and did not pass on.

**Everything derived from an area, however, is still hardcoded, and a new area silently gets nothing.** `getDeliveryRoute()` (`src/lib/utils/format.ts`) maps five specific area names to Route 1 or 2 and returns `null` for anything else; the Route labels in `deliveries-client.tsx` name the same areas; and the BSD Baru/BSD Lama split in the webhook is a longitude comparison. Adding an area to a kitchen therefore makes it orderable but unrouteable. That is open work, not a rule — see the queue (`pnpm tasks`).

### Deadlines, assignment and data rules

- Order deadline: 16:00 WIB the day before delivery — read from `settings.order_deadline_hour` (`order_deadline_daily_hour` for the daily-quota flow); both are `16`. Never hardcode the hour, and never state it from memory: the docs said 8pm until 2026-08-20 while the setting had been 16 since 2026-07-08, so a message written off the doc quoted customers a cutoff four hours later than the one the bot enforces.
- **16:00 is our cutoff, not the kitchen's.** Thenie accepts additions and changes for the next day until **18:00 WIB**; the two hours in between exist so the sheet can be checked before it is handed over, not because the food cannot be cooked. So an admin fixing our own mistake can still add a row between 16:00 and 18:00 by hand — that is how the 25 Agustus rows were recovered on 24 Agustus at 17:2x WIB. It changes nothing the bot may say: it enforces 16:00 and must never offer the later window, because the slack is the safety margin and spending it on ordinary requests removes it.
- After the 16:00 cutoff, orders schedule for day after tomorrow
- An owner can manually override the deadline with a warning popup
- Which kitchen serves a customer is **assigned manually by an admin, never automated** — and the candidate kitchens are only those whose `delivery_areas` include that customer's area *and* that are active. Never state a count of kitchens, or name one, from memory: this line named two of them until 2026-08-21, by which point one of the two was inactive and two more had been added. Query `subcontractors` instead.
- **`orders.order_type` is gone** (dropped in migration 063). It claimed to record a product choice — `recurring` vs `scheduled` — that never existed, and it did not even record that reliably: it defaulted to `'recurring'` on every insert, so 252 of 301 active orders said `recurring` while their `meal_time_preference` said `per_day_decision`. Every delivery-generating query filtered on `order_type = 'recurring'`, which left the daily sheet's Generate button one click from writing lunch *and* dinner rows for all 252. The only real question those filters asked — can this order's days be worked out without asking the customer? — is not asked any more: the customer's days are on the order, in `requested_schedule`. `meal_time_preference` followed `order_type` out in migration 077 for the same reason both existed, and on 2026-08-28 the machinery that stood behind them went too — `buildRecurringDeliveryRows()`, `portionsInRange()`, `getFixedMeals()` and `FIXED_SCHEDULE_PREFS` are all deleted, along with the Assistant's `create_order` tool, its only remaining admin caller. Nothing infers a schedule from a pattern any more: `delivery_schedule` is a required field of `extract_order`. Do not add a new flag.
- **Which order a delivery draws from is decided by `pickDrawOrder()` (`src/lib/orders/pick-draw-order.ts`), never by query order.** The rule is: the oldest active order that still has unbooked quota — `unbookedByOrder()`, counted from the delivery rows, since migration 075 dropped the stored counter; if none does, the most recently created active order. Four call sites previously queried `orders` filtered on `status = 'active'` with no `ORDER BY` and took the first row — `addable-customers`, `bulk-create`, the daily-sheet POST, and the since-deleted `generate-deliveries` cron. Postgres returns heap order, which is roughly insertion order, so the oldest active order won every time, including after it was fully drawn down and including when the customer had since bought a fresh package. Julian S is the case that surfaced it: order `eb853b86` (pkg 5) took 9 deliveries while `0831e475` (pkg 5, created nine days later) took 1, and only stopped winning when it flipped to `completed` and left the filter. 85 customers hold two or more active orders at once, so this was never a one-off. Do not reintroduce a bare `.limit(1)` or first-row pick on active orders.
- **Misattribution is only visible from the order side.** The customer ledger (`GET /api/customers/[id]`) sums every delivery a customer has without looking at `order_id`, so it balanced perfectly all through the Julian S bug. `GET /api/orders/[id]/ledger` shows one order's own credit and draws, so a delivery charged to an exhausted package reads as a running balance going negative. It is rendered in the Orders detail slide-over as "Draw history" and is the view to check after any bulk re-pointing of `daily_deliveries.order_id`.
- **The Customers page loads every customer, because three of its columns do not exist in the database.** Remaining, Next Price and State are computed in the browser from the customer's orders — so Postgres cannot sort or filter on them, and over a 200-row page the browser would rank the first 200 and present it as the answer. It is not hypothetical: the three largest quota balances (Vanessa 152, Vivi 152, Eleazar 90) sit at rows 287, 289 and 296 of 336 under the page's own ordering, so "sort by Remaining, descending" on the old paged query could never have surfaced any of them. `customers-client.tsx` now pages both `customers` and `orders` to completion with `fetchAllRows()` (`src/lib/supabase/fetch-all.ts`) and filters, sorts and paginates over the complete set — architectural principle 9, and the same helper that fixed `query_leads`. Every column carries a Sheets-style header popover (sort, a condition filter, and a value checklist whose options are counted over the rows surviving every *other* column's filter), a column picker exposes ten more fields, and filters / sort / page / visible columns live in the query string so a filtered view is a link. Do not reintroduce a server-side `.range()` page or a `count: "exact"` total here.
- **Those three columns are derived one way each, and each way was wrong once.** Fixed 2026-08-30, after galvent's row read `13 / Rp 28.385 / cancelled by admin` while she had 8 porsi left at Rp 29.000 on a live order.
  - **Remaining** is everything the customer bought minus everything they have eaten — package credits over `active` / `paused` / `completed` / `payment_proof_received`, minus every `daily_deliveries` row dated on or before today, counted **per customer and not per order**, floored at 0. That is the same pair of sums the ledger drawer shows as `balanceToday`, so the list and the drawer now answer with one number. It used to be computed per order, each order's remainder floored at zero and the positives summed, which turned one order's over-draw into free portions on another: the 2026-06-08 import gave most customers a `package_size = 0` catch-all order dated 2026-06-24 carrying their whole migrated delivery history, so the catch-all sat far below zero and was discarded while the real packages — whose rows are all on the catch-all — still read full. 60 balances were overstated (galvent 13 for 8, Hanna 18 for 4). **Never floor a balance per order**; attribution is not sound enough to survive it, and a customer-level balance does not depend on attribution at all. Crediting `completed` is part of the same fix and cuts the other way for 8 customers whose completed packages have no delivery rows at all: they gain 110 porsi between them, Vanessa's 38 the largest. That number is not new — the drawer has shown it all along — and if it is wrong it is wrong in one place now.
  - **Next Price** is `pickDrawOrder()`'s answer: the `price_per_portion` locked on the oldest active order that still has undated portions. It replaced an "Avg Price" that recomputed migration 035's weighted average on read — a portfolio blend on a FIFO ledger, so galvent's Rp 28.385 across a 29.000 and a 28.000 order was a rate nothing had ever charged and nothing ever would. The URL column key changed with it (`derived_avg_price` → `derived_next_price`), so a bookmarked `?cols=` naming the old key drops the column; that is deliberate, the column no longer means what the bookmark asked for.
  - **State** is the customer's own lifecycle state, overridden by their newest order's status **only while that order is live** (`hasCurrentOrder()`). A terminal status — `completed`, `refunded`, any cancellation — never becomes a state, because what the customer is once an order is over is exactly what `customer_state` already says. The caller took the newest order by `created_at` regardless of status, and galvent held three orders created within 46 minutes on 2026-08-19: a live 10-porsi package at 06:32 between cancelled duplicates at 06:06 and 06:52. The duplicate cancelled *after* the live one owned her badge. 64 customers carried a terminal status as their state, most of them `completed`. Pinned by `test/customer-display-state.test.ts`.
  - The page's `today` is `jakartaDateString()`, not `new Date().toISOString()`. Railway runs UTC, so between 00:00 and 07:00 WIB the old line named yesterday and every delivery dated today dropped out of the balance.
- **`customers.portions_remaining` and `customers.avg_price_per_portion` are dead columns — never read them.** They are the unfinished half of migration 035, which set out to replace per-order balance tracking with a customer-level Weighted Average Cost model and never removed the thing it was replacing. Both models then ran at once with nothing keeping them equal: 65 of 333 customers had a wrong balance and 127 a wrong average price (one showing Rp 32.333, above any tier that has ever existed; several negative, which the `> 0` render silently hid as "—"). Six code paths wrote them; a single cell on the Customers page read them. That cell now derives both without reading either column — see the bullet above for how — so the page agrees with Orders and the customer ledger. The columns still exist and are still written — dropping them is gated on the reconciliation chain, because 27 customers hold a cached balance with no order behind it (Michelle Nathania's 30 portions being the largest) and deriving turns those to 0. Every decision path already counts the delivery rows; keep it that way. `orders.portions_remaining` was the same idea one table over and was dropped outright in migration 075 — this pair survives only because 27 customers hold a cached balance with no order behind it.
- **`customers.phone_number` is canonical `+62...` and unique** (partial unique index, migration 065, skipping `IMPORT_` slugs). It previously had neither normalization nor uniqueness, so the same person existed twice as `+628...` and `628...`: the WhatsApp flow created one row on 2026-06-08 and `fix-no-orders.ts` created a second on 2026-07-07, each unaware of the other. Orders landed on one row and deliveries on the other. This is what made the ORDER_HARIAN audit report 135 missing deliveries — matching sheet names to a single customer id picked the empty twin. The real number is 5 (Elaine 3, Daryn Dior 1, rudy 1). `scripts/dedup-phone-format.ts` merged the 11 groups on 2026-08-14, re-pointing `orders`, `conversations`, `daily_deliveries`, `broadcast_recipients` and `delivery_proofs.matched_customer_id`, dropping the duplicate's `customer_flags` / `customer_state` / `customer_rate_limits` rows, then deleting the emptied row. It never deletes deliveries — the older `scripts/dedup-customers.ts` does, and is only correct for `IMPORT_` placeholders.
- **The 2026-06-08 import invented placeholder orders** — fixed 2026-08-14 by `scripts/fix-placeholder-orders.ts`. Defi Lugito (`pkg=16`), Valen (`pkg=45`, exactly the sum of her two real orders) and Darren (`pkg=18`) each carried a fabricated order on the WhatsApp row that is in no sheet, while their real purchases sat on the duplicate row. Merging the duplicate rows made both sets count as purchases and *masked* the overdraw, which is why any bought-vs-drawn figure taken between the merge and this fix is wrong. The placeholders are deleted, every delivery re-pointed to a real order by the `pickDrawOrder()` rule, and Darren's real June package (30 porsi, Rp 790.000 @ 26.333) written for the first time. Verified balances: Defi 100/106 = −6, Valen 45/49 = −4, Darren 30/33 = −3. Darren also held copies of Darren Dior's 10 March deliveries, deleted the same day.
- **Darren, Darren Dior and Daryn Dior are three different people.** Darren (`+6281262652288`) bought his own 30-porsi package in June. Darren Dior draws from his sister Daryn Dior's 16-porsi order `26744cb1` via `customers.linked_order_id` — his 10 March deliveries plus her 6 are that one package, so neither is an overdraw. `scripts/fix-linked-order-draws.ts` wired this up on 2026-08-14 — his 10 rows and her 5 now draw from `26744cb1`, leaving it at `rem = 1`. Before that his rows drew from his own `pkg=0` import artifact `2b9d5067` and hers from artifact `feb481a3`, so the real order sat untouched at `rem = 16` and both siblings read as overdraws. Both artifacts are now empty and are left in place for the wider ghost-order cleanup. Her sheet shows 6 deliveries against 5 in the database — that missing row is the "Daryn Dior 1" in the ORDER_HARIAN audit's remaining 5, and it would take `26744cb1` to exactly 0.
- **Only `addable-customers` honours `linked_order_id` when choosing a draw order.** The daily-sheet POST and `bulk-create` both call `pickDrawOrder()` on the customer's own orders, so a new delivery for a linked customer charges their own (usually `pkg=0`) order rather than the package that actually covers them. Only Darren Dior is linked today, and he has not ordered since March, so nothing is currently mis-drawing — but any new linked customer will need the other three paths fixed.
- **"Sisa kuota" is two different numbers, and `unbooked` is the one customers do not mean.** `unbooked` counts portions **not yet booked onto the calendar**; what a customer means when they ask how much they have left is portions **not yet delivered** (`remainingToday`). Both are counted from the delivery rows — `orders.portions_remaining` cached the first, was read as the second, and was dropped in migration 075. The gap is not small: on 2026-08-20 Nadya's 20-porsi package had 0 unbooked with twelve meals still to come, every one of them already dated through 8 September. The ledger route has carried both since it was written — `remaining` (all draws) and `remainingToday` (draws dated on or before today) at `src/app/api/orders/[id]/ledger/route.ts` — and `loadCustomerSchedule()` (`src/lib/orders/customer-schedule.ts`) computes the same pair for the bot. The counter read the way it did because two write paths disagreed about when to decrement: `book_delivery_dates` deducted when the dates were booked, the `deduct-daily-quota` cron when the food went out. A single number cannot be both, which is why it is gone rather than repaired. Treat `unbooked` as "how many more dates this customer may ask for" and nothing else. Reading it as the undelivered balance tells a fully-paid customer their package is finished, and is the same conflation that made three customers look overdrawn in the 2026-08-20 sheet audit when their books balanced exactly. **The bot still quotes the wrong figure to customers sometimes, so an admin verifies before answering a balance question**: Customers → the customer → *Riwayat pemakaian*, where each package is a `+N`, each daily draw a `−N`, and *Sisa hari ini* is the balance that counts (`GET /api/orders/[id]/ledger`). The handbook (`/handbook`, section 8) tells new admins to check it rather than repeat what the thread says.

- **An order is completed on what it has actually delivered — `orderRemainingToday()`, never on what it has booked.** The unbooked figure reaches 0 when the calendar fills, not when the food goes out, and the stored counter that held it (dropped in migration 075) did the same: `deduct-daily-quota` deducts *tomorrow's* rows and the daily-sheet PUT deducts on save. Completing on it closed four orders still owing 35 portions between them — Febby 20, Nadya 12, Kurniadi Tan 2, Jordy 1. Nadya's closed on 2026-08-13 holding twelve undelivered meals, which left her with no active order at all, so the bot lost her quota context and `activeOrder` came through null on every message. Two of the four were closed the same day `scripts/reassign-draw-orders.ts --apply` ran: it recomputes `portions_remaining` as `package_size - every non-cancelled delivery row` with **no date filter** (line 158), so a fully-*booked* order lands on 0 and the cron closes it on the next tick. The cron now calls `orderRemainingToday()` (`src/lib/orders/customer-schedule.ts`), which counts only draws dated on or before today. The older rule below still holds for the customer counter. **Repaired on 2026-08-21** with `scripts/reopen-underdelivered-orders.ts --apply`: four orders reopened — Febby `19aabe69` (owed 20), Nadya `0e20e551` (11), Lina Marlianty `1a274dc3` (1), Kurniadi Tan `3c96151b` (1). Lina's was missed by the first audit, which measured with the stored counter — the very column at fault; recount from `daily_deliveries` rows, never from `portions_remaining`. Jordy's `22e8930a` needed no repair by then: his last portion shipped on 21 Agu, so the order completed legitimately. The script targets only orders carrying a `completed_at`, which is what this cron writes. Four others sit `completed` while still owing food (Nabila, Tia ×2, Febby `a7946adf`) with no timestamp and no future rows — closed by some older path, deliberately left alone.

- **An order is never completed on the customer counter.** `deduct-daily-quota` used to key completion on `customers.portions_remaining` and close *every* active order a customer had the moment that counter reached zero. The counter was only ever credited by `POST /api/customers/free-quota` — `POST /api/orders` set `orders.portions_remaining` and left the customer counter alone — so a purchased package left it at 0, `Math.max(0, 0 - n)` read as "exhausted", and the order closed with its package untouched. Jordy's 5-porsi order was completed on 2026-08-13 holding 4 portions, which blocked his next delivery behind the "Customer has no active order" guard. Fixed both ends: the cron now deducts per order first and completes only orders whose own balance hits ≤ 0, and order creation credits the customer counter (and debits it again for backfilled past slots). Three orders were reverted to `active` by hand — Jordy (4), Nicholas Satria (2), Cindy Angelia (1). Seven other `completed`-with-balance orders carry `completed_at = null` and came from import scripts, not this bug.
- **A delivery row is present or absent, and skipping deletes it** (migration 075). `daily_deliveries` has no `status` column. It had one for the whole life of the table and it said `'scheduled'` on all 2937 rows it ever held, while seven read paths each had to remember to carve out values nothing ever wrote — and two of them already disagreed with each other. A skip goes through `deleteDelivery()` (`src/lib/orders/delivery-state.ts`), which copies the complete row into `edit_log` before removing it, because `order_id`, `subcontractor_id`, `address_slot` and `portions` cannot be recovered from the conversation that asked for the skip. **Nothing else is written**: every balance is `package_size` minus the rows that exist, so deleting the row *is* the refund — never hand the portions back to a counter, and never mark a row instead of removing it. Whether a delivery has happened is derived from its date (`date <= today`); whether it can still be skipped is `isLocked()` — past 16:00 WIB the day before, the sheet has gone to the kitchen, we owe for the portion either way, and the answer to the customer is an escalation rather than a delete. Dropping the counter took two migrations, not one: `orders.portions_remaining` had been `NOT NULL` with no default since migration 003, so code that omits it fails against a database that still has the column and code that supplies it fails against one that has dropped it — either ordering leaves every order insert failing for the length of a Railway build, the bot's included. 074 drops the constraint (safe for both versions of the code at once), the deploy goes out, and only then does 075 drop the column. **Any future drop of a `NOT NULL` column needs the same two steps — and the two steps are two pushes, not two files in one commit.** Pushing to `main` applies pending migrations to production by itself (see "Migrations apply themselves on push to main" in `DATABASE.md`), so committing 074 and 075 together dropped the column while the old code was still live for the length of the Railway build. No order was inserted in that window, so nothing failed, but the ordering the two migrations existed to guarantee was gone. Dropping the counter moved the has-quota verdict for **51 active orders** that the dashboard, the renewal cron and the addable lists were still reading it for: 42 the counter called exhausted while the rows say they have quota left, and 9 the other way. The bot had been on the derived figure for all of them since 2026-08-24.

- **The sheet generators check unbooked quota before writing a row** (`unbookedByOrder()`, `src/lib/orders/customer-schedule.ts`). `status = 'active'` plus a standing `meal_time_preference` used to be the whole test, so a fully-booked order kept generating rows past its package: on 2026-08-20, **21 of the 28 rows** the generator built for the next day were already over-draws, and an admin had to cancel them by hand. The guard counts **every** row on the order against `package_size`, because every row that exists is food that will be cooked: a skipped or cancelled delivery is a deleted row now, not a marked one (migration 075). It decrements per meal, so a `both_fixed` order with one portion left writes lunch and not dinner rather than overshooting by one. This guard is what makes reopening a wrongly-completed order safe, and it is load-bearing for that: without it, an order back on `active` generates a fresh row forever.
- **Goodwill portions are granted as their own order, never by bumping a paid one.** `POST /api/customers/free-quota` inserts a Rp 0 `orders` row with `source: 'free_quota'`, a `grant_reason` and `granted_by`, so the grant reads as a discrete `+N` line in the customer's ledger. Raising `package_size` on the customer's paid order instead makes the grant invisible and misstates what they bought: Fahmi's +1 for the 24 Agustus delivery that was never written turned his 20-porsi purchase into a 21-porsi one, his ledger showed no grant at all, and the only record was an `edit_log` entry nobody reads. Corrected on 2026-08-25 — the paid order went back to 20, the portion was re-issued as free-quota order `4955fb91` carrying the original reason and grantee, and the last delivery row (11 September) was re-pointed onto it so the booked rows still balance against what was bought.
- No *manual* draw path checks the balance before writing, so a fully-used order can still go negative. The reconciliation ran on 2026-08-13 (`scripts/reassign-draw-orders.ts --apply`): 805 deliveries re-pointed by FIFO and 84 `portions_remaining` counters recomputed from actual draws. Of 289 active orders, 209 now read ≤ 0 and **28 are strictly negative** — the ≤ 0 count went *up* from the pre-run 89. That was read at the time as fully-drawn orders correctly reading 0; it is not, or not only. The script counts future scheduled rows as draws, so a fully-*booked* order reads 0 with its food still to come, and the completion cron closed Nadya's and Kurniadi Tan's that same day. Recompute with a date filter before trusting any of those 209 as exhausted. The 28 are genuinely over-delivered. A hard reject in daily-sheet `PUT` is now unblocked for the reconciled set, but 72 customers holding a `package_size = 0` order were excluded from the run and must be backfilled first, or the guard will reject their legitimate deliveries.
- **Both of the rules that used to live here are gone with the code they described** (2026-08-28). "Ranged generation is capped by the package" and "a stated date range is the package size" both existed because a schedule could be *derived* — from a start/end range and a meal pattern — and a derived schedule has to be defended against the range being longer than the package (a replay on 2026-08-19 wrote 10 rows against Fidela's 8-porsi order) and against the model's own arithmetic about the range (Nadya was sold 22 porsi against a 20-day range while 20 rows were written). Nothing derives days now: `delivery_schedule` is required, `package_size` is the sum of its slot portions, and a customer who names no days has no dates at all. The kept guard is the one that does not depend on any of it — the sheet generators still refuse to write a row an order has no unbooked quota for.
- **Money that has moved outranks every number in the conversation.** The bot calls a 10-day lunch+dinner package "paket 10 porsi", so its own price list conflates days with portions: Kurniadi Tan pasted a BCA receipt for Rp 540.000 on 2026-08-04 and the order was written for 10 porsi at Rp 280.000 — half of what he paid. `statedTransferAmount()` reads the rupiah figure off an inbound message that looks like a receipt (a bare price the bot quoted is not money that moved), and `createOrderFromExtraction` uses the package size whose total equals it. Precedence for `package_size` is now: paid amount, then the last bare total the customer stated, then a duration in weeks, then the delivery range, then the model's number floored at the smallest tier. The stated-total step is what catches a customer changing their mind — Tiwi asked for 8 porsi, was told 8 is off the list, wrote "Boleh 6 porsi dulu kak", and the order was still written for 8. A stated total below the smallest package is describing a delivery ("1 porsi"), not the order, and is ignored.
- **A duration in weeks is a portion count, and our week is Senin–Jumat.** Lina Marlianty wrote "2 minggu dl aja.. 1 porsi" and was asked whether she meant 5 or 6 days three times running; recovery then sold her 18 porsi for an order that was 10 porsi of lunch. `statedWeeks()` reads the duration and the size becomes weeks × 5 × portions per delivery day, unless the customer also stated a bare total or the extraction carries an explicit `delivery_schedule`. Sabtu is opt-in — asking which is never worth holding an order open for.
- **A `both_fixed` no customer message supports is downgraded to `lunch_only`.** Siang is the documented default, and dinner doubles both the portion count and the price, so the model guessing it turns a 10-porsi order into an 18-porsi one. `createOrderFromExtraction` scans the customer's own messages for malam / dinner / keduanya and downgrades when none of them appears.
- **A day pattern the customer states is not carried into the generated schedule (unfixed).** Generation only knows Senin–Sabtu minus closures; "weekdays only" or "tiap jumat libur" is read by the model, restated back to the customer, and then thrown away — nothing on `orders` records which weekdays a package runs on. Auditing the 20 Agustus sheet on 2026-08-19 found Sherine Fayola booked on three Sabtu after saying "Catatan weekdays only" twice, and Lina Marlianty booked on every Jumat after saying "tiap jumat libur". Both schedules were rebuilt by `scripts/fix-sheet-audit-0820.ts`, which also repointed galvent's kitchen-less 20 Agustus row and Tio Jason's four rows still pointing at Perut Bahagia (retired in June) — `/dapur/[id]` filters strictly on `daily_deliveries.subcontractor_id`, so either value makes the row invisible to the kitchen that has to cook it. The durable fix is a per-order weekday mask; until it exists, a stated pattern has to be corrected by hand after the order is paid.
- **Delivery runs Senin–Sabtu.** `isDeliveryDay()` (`src/lib/holidays/id.ts`, moved there when the generator it lived in was deleted) was `isWeekday()` (Mon–Fri) and was never updated when Saturday delivery went live, so no fixed-schedule order could generate its sixth day: every 6-day package came up one delivery short with nothing reporting it, and Julian S's 18–22 Agustus package wrote four days for five portions. Minggu stays closed, and so is every **libur nasional** — `isDeliveryDay()` calls `isClosedHoliday()`, because `record_daily_order` has filtered closures since the holiday file was written while generated schedules did not, and galvent's package was booked straight through 25 Agustus (Maulid Nabi). Cuti bersama is deliberately not filtered: whether the partner kitchens work those days is an `ask_admin_for_help`, not a closure. **A libur nasional the active kitchens work through anyway goes in `OPEN_DESPITE_HOLIDAY`** (`src/lib/holidays/id.ts`), which `isClosedHoliday()` checks first — closure is a property of a kitchen and this table is global. 2026-08-25 (Maulid Nabi) is in it: Veronica Catherine asked on 23 Agustus to start Senin 24, the H-1 16:00 cutoff had passed by two minutes, so `earliestDeliveryDate()` moved to Selasa 25, found the holiday, and moved again to Rabu 26 — costing her a delivery day the kitchen serving her was open for, and the bot told her so in writing. A date belongs there only when **every** active kitchen works it. That is a low bar while one kitchen takes standing orders and a real one the moment a second does, so revisit the set before reactivating one: a wrong entry promises deliveries nobody will cook. `isDeliveryDay()` is the one question to ask: `mark_paid` filters `requested_schedule` through it, so a Minggu or a tanggal merah the model wrote into a schedule leaves its portions unbooked rather than reaching a kitchen sheet. That is also the fix for a gap that lived here until 2026-08-28 — the filter asked `isClosedHoliday` alone, and a model-named Minggu passed straight through it.
- **`record_daily_order` books a whole run in one call, and the webhook runs every tool the model returns.** Both halves were broken and either alone loses deliveries. The tool took a single `delivery_date`, and the reply parser kept only the *last* `tool_use` block (`for … if (block.type === "tool_use") toolUse = block`), so a model that correctly emitted five calls would still have written one row. Tio Jason is the case: on 2026-08-18 he asked for Senin–Jumat siang from Rabu 19 Agustus, the bot read back the full eight-day plan, he said "iya" — and exactly one row was written, for 19 Agustus. His order is `per_day_decision`, which auto-generation deliberately skips, so nothing would ever have filled the rest in. The remaining 6 days were written by hand (`scripts/fix-tio-deliveries.ts`). The tool now takes `delivery_dates: string[]`, `portions` means portions **per date** (the tool multiplies), it skips dates already on the sheet, it books only as many days as the customer's undated portions cover, and it pushes a **high**-priority alert when the quota covered fewer days than the customer was promised. The prompt tells the model to send every ISO date in one call, to resolve weekday names itself, and not to ask a second "mau saya pesankan?" for a schedule already confirmed. `delivery_date` is still read on input because old histories carry it and the model copies what it sees.
- **The bot's booking quota is counted from the delivery rows, never from `orders.portions_remaining`.** Both the gate inside `record_daily_order` and the prompt's booking rules read `unbooked` from `loadCustomerSchedule()`. The stored counter it replaced was only correct while every path that touched a delivery row remembered to update it, and several did not — the daily sheet's × deleted a row and left the counter where it stood. Counted on 2026-08-24, the counter disagreed with the rows for **63 of the 195 customers holding an active order**, in both directions: Sherine Fayola's read 32 bookable against a package already fully dated and two portions over, so the bot would have kept selling her dates that do not exist; Vania's read 0 with ten portions genuinely left, so the tool bailed and three dinners the bot had already confirmed to her were never written. The gate is **customer-wide**, because quota belongs to the customer rather than to one package, and which package a row bills to is `pickDrawOrder()`'s decision (see above) over every active order — a `meal_time_preference` match is preferred but never allowed to exclude the only package with balance, which is the filter that lost Vania's dinners. A customer with genuinely nothing left produces a **high**-priority push, never a silent `return`. The dashboard and the crons were the last readers of the counter and now derive it too; migration 075 dropped the column. Switching the gate changed behaviour for six customers — Sherine, Lina Marlianty, Tiwi and Julian S can no longer book new dates (every portion they hold is already dated, and they are still owed the food), while Febby and Veronica Catherine can book again.
- **`record_daily_order` drops libur nasional dates itself.** The prompt has listed upcoming closures since the holiday file was written, and the model still scheduled straight through one — asked for Rabu–Jumat plus Senin–Jumat in the simulator it returned all eight dates including 25 Agustus (Maulid Nabi). `isClosedHoliday()` / `holidayOn()` (`src/lib/holidays/id.ts`) now filter the run server-side, and admins get a **high**-priority push naming the skipped holiday, because the customer may have been promised that day. The prompt rule ("skip any date marked TUTUP in Upcoming closures, and tell the customer") is the first layer and does work once it points at the section by its real name — but it is instruction, not enforcement. Cuti bersama is **not** filtered: it stays an `ask_admin_for_help`, per the existing rule.
- **The bot must propose one schedule, not two, and treat a bare "iya" as confirming it.** Tio Jason's live thread and a replay of it both ended in a clarification loop: offered "mulai besok Rabu atau mulai Senin depan?", he answered "iya", and the bot asked again rather than booking. Nothing was recorded either time. The daily-quota prompt section now forbids either/or questions, says an affirmative confirms the schedule just proposed, and forbids asking the same clarifying question twice — after one failed attempt the bot states the dates it is recording and books them. A customer who has already given days and meal has said enough.
- Nothing auto-generates a schedule any more. The days come from the customer, are stored on the order at creation, and become rows at payment.
- **Delivery rows are written when the order is marked paid, not at creation and not nightly** (migration 076). The customer's days are stored on the order as `requested_schedule` at creation and turned into rows once, by `mark_paid` (`PATCH /api/orders` and the Assistant's `mark_order_paid`), filtered through `isDeliveryDay()`. An order whose `requested_schedule` is null — the bebas customer who named no days — gets rows only as they ask for them, through `record_daily_order` or a human on the sheet.
- **There is no nightly generator, and there never was one.** `/api/cron/generate-deliveries` was deleted on 2026-08-25 after it was confirmed dead: it was never in the `JOBS` table in `src/lib/cron/scheduler.ts`, there was no Railway cron service, and `edit_log` held **zero** rows with `action = 'cron_generate'` although the route wrote one on every run including empty ones. It had therefore never executed once in its life while reading, to anyone opening the repo, like a safety net — `/guide` taught admins it ran at 17:00 daily, and Fahmi's missed 24 Agustus resume was left to it. Do not re-add it.
- **The sheet says what changed since the last day we cooked.** `DiffPanel` in `src/components/dashboard/deliveries-client.tsx` sits above the Deliveries sheet and compares the selected date against `previousDeliveryDay()` (`src/lib/deliveries/diff.ts`) — the previous *delivery* day, skipping Minggu and libur nasional, or every Senin reads as the whole book cancelling over the weekend. Collapsed it is a line: how many customers are new, how many stopped, how many changed size, and the day's portion total before and after; opened it names them. `diffSheets()` keys on customer **and meal**, not on the row id — a customer who skips a date and rebooks it gets a new row id for the same meal, and reading that as one person leaving and another arriving is the opposite of the answer — and sums portions per key, since a customer holding two orders can draw a row from each on one meal. It diffs the rows on screen rather than the saved ones, so unticking a row shows in the panel before the save lands. The comparison day is fetched under the same `["daily-sheet", date]` query key the sheet itself uses, so stepping a day forward reuses what was already loaded.

- **The second generator is gone too** (2026-08-25). `POST /api/deliveries/daily-sheet` carried the same logic behind the Deliveries page's Refresh button, which called it only when the sheet for that date had **zero** rows and otherwise just refetched — one label, two behaviours. It was argued for as the repair path for an order whose schedule ends short; it could never have been one. Every working day through 22 September already held rows, so the first date it could fire on was a month out, past every current order's end. On such a date it would not repair anything: it would book a month of portions early against whatever `meal_time_preference` the order still carried, with no holiday or Sunday guard and without setting `address_slot`, so split-address customers would lose slot 2. The only state in which it acted was the state in which it did damage. Refresh now only refetches — and even that is belt-and-braces, since every mutation already invalidates the query. **The delivery sheet is a stored table read straight back, not a derived view**: rows enter `daily_deliveries` when an order is marked paid (from its `requested_schedule`), from the bot's `record_daily_order`, or from a human on the sheet. Nothing generates them on read, and nothing should.
## The days are part of the order brief, and the bot must have them before it sells anything

`delivery_schedule` is a **required** field of `extract_order`, and `[]` — an empty array — is the answer for a customer who books day by day. A call that leaves the field out is refused: `createOrderFromExtraction` writes nothing, asks the customer which days they want, and lets the model call again next turn with the answer. No bank details go out, because creating the order is what sends them.

It was optional until 2026-08-28, and a missing schedule was filled in from a meal-preference enum: `lunch_only` / `dinner_only` / `both_fixed` / `default_*` were standing patterns that filled the package's whole run of days from `start_date` without asking anything further. galvent wrote "Jdwal tdk menetap" and asked for tomorrow only ("Bsk mao — Nanti selanjutny diinfo per 1 hari sblomnya"); his 10-porsi order was created through the Assistant as `dinner_only` at 2 porsi per delivery, and five days (20, 21, 22, 24, 25 Agustus) were booked for him — the package read as fully spent on the day he bought it, and 25 Agustus is Maulid Nabi.

The refusal is the same shape as the name guard, and carries the same risk: a required field is one more way for an order to die in the chat. `[]` is what keeps that from happening — it is always available, the tool description says so, and the prompt tells the model to ask once and send `[]` if the answer is not dates. **The Assistant has no order-creating tool any more.** `create_order` took a meal preference and expanded it, which is the exact thing being removed, and `edit_log` records it as never once used since assistant-tool logging went live on 2026-08-21. An admin creating an order by hand uses the New Order form on `/orders`, which takes the days.

## Marking an order paid never regenerates a schedule it already has

Both `mark_paid` paths (`PATCH /api/orders`, assistant `mark_order_paid`) used to rebuild the schedule from a meal pattern unconditionally, so payment landing rebuilt the standing Senin–Sabtu pattern on top of whatever was already there. An order created from an explicit `delivery_schedule` already carries the days the customer asked for, and those days are usually a *subset*: Tiwi's 6-porsi order was written for 19, 20, 21, 24, 26 and 27 Agustus, deliberately skipping Sabtu 22 and Maulid Nabi on the 25th. The upsert's `ignoreDuplicates` only stops an exact collision, so the two days her schedule had skipped were inserted — 8 draws against a 6-porsi package, and one of them on a closure. Both paths now check `orderHasDeliveries()` (`src/lib/orders/order-has-deliveries.ts`) first. A schedule that exists is the customer's; regenerating can only pad it back out to the default.

Not fixed by this: `resizePendingOrderFromMessage` shrinks a package but calls `fillMissingSchedule`, which only ever touches an order with **zero** delivery rows — so a size reduced after a schedule exists leaves the surplus days in place. Nothing has hit it yet.

**And `mark_paid` does not cap the rows it writes at `package_size` — it charges each one to the order that owes it instead.** A top-up is sized net of what the customer still holds — 7 days wanted, 1 porsi left, paket 6 (see "A leftover porsi is spent before a new package is sold" in `BOT_RULES.md`) — so its schedule is legitimately one day longer than its own package, and a cap would drop a meal the customer has already paid for.

Both `mark_paid` paths stamped their own order id on every row, so Veronica Catherine's seven days on 2026-08-30 all landed on the new 6-porsi package: it sat 1 over its own size while her June order kept a portion it had been paid for and could never complete. The row was repointed by hand the same evening (`edit_log`, `repoint_order`).

`buildPaidDeliveryRows()` (`src/lib/orders/paid-delivery-rows.ts`) is what both paths call now. It drops the Minggu and libur nasional as before, sorts the days into delivery order, then walks them against the customer's active orders through `pickDrawOrder()` — oldest package with balance first, exactly the rule every other draw follows — decrementing a running balance as it goes. The order being paid is the fallback, and always a candidate for its own days: a row nobody charges is a meal that never reaches a kitchen, so it takes whatever the older packages cannot cover. **A row is indivisible** — `daily_deliveries` is unique on `(delivery_date, customer_id, meal_type)` — so a 2-porsi row against 1 porsi of balance goes whole to that order and takes it one over. That is the only over-draw the path can still produce, and it nets to 0 at the customer level, which is the level every balance is read at.

## The ledger dates a package credit by when it was bought

Both ledgers date the `+package_size` row with `packageCreditDate()` (`src/lib/orders/credit-date.ts`), which is the **earliest** of `created_at` and `start_date`. Neither column alone is the purchase date:

- `start_date` is when the package starts *running*. Dating the credit by it put galvent's 19 Agustus purchase on the 20th and Veronica Catherine's 23 Agustus purchase on the 26th — under the deliveries drawing from it, so the running balance went negative for three days on quota she had already paid for. 250 of 451 orders have a `start_date` on a different day from their creation, so this was every customer's ledger, not one bad row.
- `created_at` is the row's insert time, which for the **182** orders migrated in bulk is the migration, not the sale — those carry a `created_at` *later* than their own `start_date`, and dating their credit by it files a May package under its own June draws.

A package cannot have been bought after it started delivering, so the earlier of the two is right in both directions. Fixed in `GET /api/orders/[id]/ledger` first (the galvent case) and left unported to `GET /api/customers/[id]` for a week, which is how the same bug came back on a different screen — the two routes build the same `+N` row and any change to how it is dated belongs in the helper both call.

- **A delivery row's kitchen is `orders.subcontractor_id` if set, else `customers.subcontractor_id`** — the order-level value is an override, not the only source. `/dapur/[id]` filters strictly on `daily_deliveries.subcontractor_id`, so a null there does not fall back at read time: the delivery is simply invisible to the kitchen that has to cook it. The delivery generators always applied the fallback; the two `mark_paid` paths (`PATCH /api/orders`, assistant `mark_order_paid`) copied `order.subcontractor_id` straight through and did not. The assistant's `create_order` compounded it by never setting the order's kitchen at all — it had no admin form to take one from — so Julian S's renewal produced five rows with a null kitchen and his 18 Agustus dinner was missing from Thenie's page while sitting correctly in his ledger. Both `mark_paid` paths now fall back to the customer; `create_order` was deleted on 2026-08-28.
- **`delivery_route` is stored on `customers`, not computed at read time**, and it is stamped from the area by `getDeliveryRoute()` in `src/lib/utils/format.ts` (Alam Sutera/BSD Lama → 1, Gading Serpong/BSD Baru/Karawaci → 2). The Daily Sheet, `/dapur/[id]` and the deliveries board all group on the stored column. Every path that *creates* a customer stamped it; until 2026-08-26 no path that *updates* one did, so a customer who changed area kept the route of the area they left — Sherine Fayola moved to Gading Serpong and stayed on Route 1, which is the wrong van and the wrong rate, since Route 1 was our own courier and the cheaper of the two until we stopped running one on 2026-09-01; the route still groups the sheet, it just no longer changes the rate. `withDeliveryRoute()` now restamps any patch that moves `area`, applied at `PATCH /api/customers/[id]` and the Assistant's `update_customer_field`; `createOrderFromExtraction` already did it inline. `test/delivery-route.test.ts` fails the build if a fourth site starts writing `area` without it. An explicit `delivery_route` in the same patch still wins — that is the Deliveries page route picker overriding the map on purpose — and a patch that does not touch `area` is left alone, so a hand-set route survives every unrelated edit. An area the map does not know yields null: 14 customers sit in Ayodhya, Bintaro, Cisauk or Graha Raya, and editing one of those addresses clears a route that was set by hand
- **Subcontractor daily bill** (`/dapur/[id]`, `src/app/dapur/[id]/page.tsx`): the summary card shows what we owe the kitchen for that day, broken down by meal (Makan Pagi / Makan Siang / Makan Malam) then by size, with the rate printed (`Ukuran S 18 × 21.000`) so the kitchen can check the arithmetic. **It bills every delivery of the date, both sizes — never the open size tab**, which exists only to split the cook's dish list; billing the tab paid a kitchen for its S portions and left its M ones off the page. Rates come from `subcontractors.cost_per_portion` (the kitchen delivers) and `cost_per_portion_route1` (the run our own courier did); a null `cost_per_portion_route1` means one rate for both routes, which since **2026-09-01 is every kitchen** — we stopped running a courier, so both route-1 columns were nulled (migration 084) and Thenie bills 21.000 (S) / 24.000 (M) on every route. Rates are read live, so re-opening an older date bills it at today's rates. Never hardcode the rates — every figure printed there is one kitchen's current value, editable on the subcontractor form. Portions on an order carrying `orders.addon_cost_per_portion` bill at route rate + addon, so one route can print two rate lines ("2 × 21.000 + 1 × 26.000") — the same grouping the COGS journal does. The page is **public and unauthenticated**, so anyone with the URL sees these per-portion costs; that is intended (the kitchen is the audience) but is why customer prices must never be added to it.
- **The link to a kitchen's page lives on Settings → Subcontractors**, in the detail slide-over: the path, an Open button and a Salin link button that copies the absolute URL. Nothing in the app linked to `/dapur/[id]` before, so sending a kitchen their sheet meant knowing the URL shape and pasting the uuid by hand — which is how two new event kitchens ended up needing the link read out of a database query. The origin is only read inside the copy handler (`window.location.origin`), never during render, so there is no hydration mismatch. It replaces the one hardcoded `/dapur/<uuid>` sidebar item labelled with a kitchen's real name, which put that name in the admin nav, could only ever point at one of them, and was removed from `allNavItems` once every kitchen had a link of its own.
- **A meal slot the page does not render is a delivery nobody cooks.** `/dapur/[id]` filters strictly on `meal_type`, and it knew only `lunch` and `dinner` — so the three morning runs of the ICE BSD event booking (21–23 Agustus 2026) were fetched and then dropped, leaving Dapur Mama Echa's page empty and her bill at Rp 0 against the Rp 900.000 she was owed. `meal_type` has no CHECK constraint; the only thing bounding it is `UNIQUE (delivery_date, customer_id, meal_type)`, which is what forces a third value for a third slot in one day. Makan Pagi now renders as its own summary line and its own two route sections, both **conditional on the day actually having morning rows** — no standing package produces one, so every other kitchen's page is unchanged rather than carrying an empty "0 porsi" line. The COGS journal needed no change: `daily-sheet/route.ts` keys `journalAccum` on the `meal_type` string itself and posts one revenue + one COGS pair per distinct value.
- **Add-ons (nasi merah and the like) are two separate numbers.** What the kitchen charges us extra goes in `orders.addon_cost_per_portion`; what the customer pays is already inside `orders.price_per_portion`, because we charge the add-on through at cost. Cindy Angelia's order `6cd37e43` is the worked example: 34.000 = the 5-porsi tier 29.000 + 5.000 nasi merah, with `addon_cost_per_portion = 5000`. Only the customer half was set at order time, so every COGS journal for her portions posted at flat 21.000 and understated cost by 5.000/porsi; the 12, 13 and 14 Agustus entries were corrected in place (both `journal_lines` amounts and the `journals.notes` breakdown) rather than reversed, on Justin's call — journals are idempotent on `source_id`, so a re-run will not rebuild them. The field is edited as "Tambahan / porsi" on the new-order modal and the Orders detail slide-over (`update_fields` allowlist). It is **per order**, so a customer's next package needs it set again, and changing it never rewrites journals already posted. That includes a `free_quota` order: Cindy's 19 Agustus delivery drew from her 1-porsi free-quota row (`85110288`), whose addon was 0, so the kitchen bill and the COGS journal read 21.000 instead of 26.000 — the nasi merah is what the kitchen cooks, so it costs us the same whether or not the customer paid for the portion. Nothing derives the addon from the customer's other orders, so **every new order for a customer who has one needs it set by hand**; when a delivery bills at the plain route rate for someone who should carry an addon, check which order the row draws from before looking anywhere else. The bot can now set it itself: `nasi_merah: true` on `extract_order` adds `NASI_MERAH_SURCHARGE` (Rp 5.000, `src/lib/claude/extract-order.ts`) to `price_per_portion` and writes the same figure to `addon_cost_per_portion`, so the two halves can no longer be set separately on an order it creates. Before that the prompt listed exactly three accepted custom requests and nasi merah was not among them — the bot told Cindy "belum bisa kami sediakan" twice and never created her order, for an add-on her real order was written with. **The add-on reaches the kitchen's bill and never its card**, though: `nasi_merah` is deliberately kept out of `catatan` (`src/lib/claude/prompts/system.ts`) because it moves the price, so it lands in `addon_cost_per_portion`, and `/dapur/[id]` reads that column for the per-portion rate only (`src/app/dapur/[id]/page.tsx`) — the customer's card says nothing about red rice. So a nasi merah order is billed correctly and cooked wrong unless an admin types it into `kitchen_notes` by hand, the same shape as Surya's `tanpa nasi`. Found in the 2026-09-01 rice audit; latent rather than live, since no order with a non-zero addon currently has a delivery row ahead of it.
- Address/area is customer-level data — `orders` has no address columns. Order pages/APIs read delivery area/address via join on `customers`. A customer move goes in `address_2`, not a new order-level snapshot. `price_per_portion`/`total_price` remain order-level (locked at creation).

## An order's real state is its delivery rows, never its header columns

Three columns on `orders` look authoritative and are not. Each one was read as truth during the 2026-08-27 sheet audit and each one gave the wrong answer.

**`end_date` is what the customer originally asked for, not when the package ends.** A reschedule moves the delivery rows and leaves the date behind. Julian S bought 5 dinners for 18–22 Agustus, moved them himself, and took them on 18, 19, 24, 26 and 27 Agustus — five rows, quota exact, against an `end_date` of 22 Agustus that has been stale since he asked. Rows outside `start_date`..`end_date` are normal and are not evidence of an over-draw; count the rows.

**An `active` order with no delivery rows at all can be a phantom, not a backlog.** Sky reads as an active 20-portion package that has delivered nothing since 17 Juli. The ledger says otherwise: her twenty portions are all booked, at 2 porsi a row across 13–17 Juli, and they hang off her **other** order — `ff2b359c`. She has **0 quota left**, not 20.

Which of the two is the real order is the opposite of what the rows suggest, and getting it backwards deletes a paid record. `442f4cb8` is the one she **paid** — ordered 11 Juli, `paid_at` 12 Juli — and it carries zero delivery rows. `ff2b359c` is a 1 Juli attempt she abandoned: she got the bank details, immediately asked for a custom split, the bot escalated it, and she never transferred. The rows were built against that abandoned order anyway. So the unpaid order holds the schedule and the paid order holds nothing; neither is "the duplicate" in the sense of being disposable. `ff2b359c` is cancelled by `cancel-unpaid` as of 2026-08-27, which leaves its July rows orphaned — harmless, since they are in the past, but they are the reason her quota reads as drawn. Before chasing an idle package, check whether its portions were drawn against a sibling order; `unbookedByOrder()` is per order and will happily report a full package unbooked for a customer who has eaten all of it.

**A small order can be a goodwill credit rather than a purchase.** Fahmi's one-portion order (`4955fb91`, dinner_only, one row on 11 September) is a free portion given on 24 Agustus, compensation for a delivery of his we failed to create that day. It is not a botched amendment and it is not a billing error. Nothing on the row says so — there is no field for "this was on us" — which is why it reads as an anomaly to every audit that looks at it.

## Order flow stages

`pending_payment` → `payment_proof_received` → `active` → `paused` (optional) → `completed`

Cancellations: `cancelled_unpaid`, `cancelled_by_customer`, `cancelled_by_admin`, `refunded`

**`cancel-unpaid` had never cancelled a single order.** It ran hourly for months, returned `ok: true` every time, and `cancelled_unpaid` had zero rows in the entire table. Its query asked for `customers(phone_number)` with no FK hint; `orders` reaches `customers` two ways — `orders_customer_id_fkey` (`orders.customer_id → customers.id`, the one meant) and `customers_linked_order_id_fkey` (`customers.linked_order_id → orders.id`, pointing back) — so PostgREST rejected the whole request with `PGRST201` and returned no rows. The route destructured only `data` and discarded `error`, so `null` fell into the `if (!orders?.length)` branch and was reported as "nothing to cancel", which the scheduler recorded as a successful run. **A broken query is indistinguishable from a healthy quiet day unless the error is read**; the route now returns 500 on a query error so the scheduler logs it and leaves `cron_runs` unstamped. The `.update()` is checked too — an unchecked failure there would have counted a cancellation that never landed, and that count is what the admin push reports. Covered by `test/api/cancel-unpaid.test.ts`.

**An unpaid order is overdue against its first delivery, not against the chat.** The first working run, on 2026-08-27, cancelled three orders and two of them were fine: Naya confirmed on 24 Aug for a 31 Aug start, Cindi on 21 Aug for a 2 Sep start, and the bot had told both of them in writing "boleh bayar H-1 atau hari H sebelum pengiriman pertama". The sweep keyed on `confirmed_at` alone, so twenty-four hours after a conversation it cancelled customers who would not owe anything for another week — and the payment-restricted WABA meant neither of them was ever told. The query now also asks `.lte("start_date", latestOverdueStart)`: past the `order_deadline_hour` (16:00 WIB) the ceiling is tomorrow, before it the ceiling is today, so an order is only swept once the H-1 deadline for its own start date has gone by. That is the same cutoff that governs ordering, changes and skips — **never reintroduce a rule that measures an unpaid order's age from when it was confirmed.** The trade-off is deliberate: an order with a distant start now sits `pending_payment` for weeks instead of being swept, and its delivery rows sit on the calendar with it. Covered by `test/api/cancel-unpaid.test.ts`.

**And the bot had to be told the same deadline.** The sweep was fixed; the prompt was not, and it still read "as long as the money lands before the first delivery" — so on 2026-08-29 Clairine was told she could transfer on Senin 31 Agustus, the morning of her own first delivery, for an order the sweep would have cancelled at 16:00 the Sunday before, silently, because by then the 24-hour window would have closed on her too. Paying on hari H was never possible anyway: 16:00 H-1 is when the kitchen sheet is booked, so an order paid on the delivery morning has no food cooked against it even if nothing had cancelled it. The prompt now names the limit as `order_deadline_hour` the day before the first delivery and requires the bot to give it as a date and a time, never as "sebelum pengiriman pertama".

**Every cancellation it makes is written to `edit_log` as `system:cancel-unpaid`.** The first working run cancelled three orders and the audit trail recorded none of them, so reconstructing what had happened meant reading `cancelled_at` timestamps and guessing. The entry carries the order's `package_size`, `total_price`, `start_date`, `confirmed_at` and the `deadline_hour` in force, which is what you need to tell a wrongly-swept order from a correctly-swept one after the fact. It is written only after the checked `.update()` succeeds — a log line for a cancellation that never landed is worse than no line.

**The same missing FK hint had silenced both payment-reminder crons.** `send-reminders` (the H-1 nudge and the abandoned-cart recovery) and `renewal-reminders` (the near-empty-quota nudge) embedded `customers(...)` unhinted, so every run returned `PGRST201` and reported nothing to send. Across the whole `orders` table `reminder_sent_at` and `followup_sent_at` are non-null on **zero** rows: neither cron has ever sent a message. Both now use `customers!orders_customer_id_fkey(...)`, which means they will start firing — though while the WABA carries the `131042` payment restriction the sends themselves still fail. Adding `orders.paid_by_customer_id` (migration 073) made `orders`→`customers` a **three**-way ambiguity, so any query anywhere that embeds `customers` from `orders` without a hint is broken, not merely at risk.

**A cancellation takes the order's undelivered rows with it.** The PGRST201 bug was hiding this: `cancel-unpaid` moved `orders.status` and nothing else, so a cancelled order's meals stayed on the calendar. Neither sheet has ever joined order status — `GET /api/deliveries/daily-sheet` keys on `delivery_date` alone and `GET /api/subcontractors/[id]/daily-sheet` on the kitchen and the date — and neither should start, because a delivery row's presence is the whole truth about whether that food gets cooked (migration 075); a status filter there would put the readers back to disagreeing about which rows to exclude. So the cancellation deletes the rows instead, through `deleteDelivery()`, which snapshots each one into `edit_log` first.

**Today onwards only.** A row in the past is food that was already cooked and delivered, and deleting it would erase a real cost from the books to make an unpaid order look tidy. The response reports `deliveriesRemoved` and `deliveriesStuck`, and a stuck row escalates the admin push to `high` and points it at `/deliveries` — a cancelled order whose meals are still on a sheet is the one state here worth waking someone for. The deletion runs inside its own `try`/`catch` after the cancellation has landed, so a failure cannot swallow the customer's notice or drop the order out of the count. Covered by `test/api/cancel-unpaid.test.ts`.

Rows still reach a `pending_payment` order by hand: the daily sheet's `PUT` accepts any `order_id` regardless of the order's status, which is how twelve of Cindi's landed on 2026-08-22. That gap is open. Of the 33 orphaned future rows found on 2026-08-27, the one belonging to the invalid `****5162` order (40 porsi, 22 Sep) was deleted by hand; the other 32 belonged to Naya and Cindi and were correct, since their orders were restored to `pending_payment`. As of 2026-08-29 no `daily_deliveries` row anywhere sits behind a cancelled or unpaid order.

`orders.status` is the source of truth for payment/subscription/order lifecycle as soon as an order row exists. `customer_state` is customer-level only (`new`, `ordering`, `lapsed`, `churned`) and should not mirror payment stages.

Payments page owns the payment queue: Awaiting payment lists `pending_payment`, admins can manually advance those rows to `payment_proof_received`, and Pending verification is where they run `mark_paid`.

The third tab carries a date picker, defaulting to today, and its label drops "today" whenever the picker is off today. **The date means when the money arrived, and every part of the tab reads the same value: `payment_proof_received_at`, falling back to `paid_at` where it is NULL.** Not the moment an admin worked through the queue, which is what Cila's card meant when it read 14.56 for a proof that landed 13.33.

Filter, sort and card all coalesce the same way, because any two of them disagreeing is visible and wrong: filtering on `paid_at` while printing the proof time put Puspa's card, reading 29 Agu 20.17, under a picker reading 30 Agu — her proof arrived that evening and was verified the next lunchtime. PostgREST cannot filter a `coalesce` without a generated column, so the query is an `.or()` of two `and(...)` branches — proof time inside the day, or proof time NULL and `paid_at` inside the day — over rows with a non-null `paid_at`. Sorting happens in the browser for the same reason, over one day already fetched whole. The day is bounded in the browser's timezone, since a UTC day starts at 07.00 for a WIB admin.

The fallback is not cosmetic: `payment_proof_received_at` is NULL on 20 of 38 paid orders (before migration 079, or marked paid without the proof step), so the card *says which of the two it is showing* — "Proof received" or "Marked paid". An unlabelled timestamp meaning two different things is the bug being fixed, not the fix.

Orders page status dropdown defaults to "Active" and has no unfiltered view by default — an explicit "All" option (empty status, no `.eq` filter applied) was added alongside the per-status options so admins can see orders in any stage.

Orders table sorts on two columns: "Start date" and "Created" (`created_at`). Clicking a header sorts by that column; clicking the active header flips direction. Only the active column shows an arrow. Default is Start date descending. The "Created" column exists to line orders up against the `package_orders` Google Sheet during data reconciliation. The leading "No." column is the row's position in the current filtered+sorted view (`index + 1`), not a stored per-order number — it always restarts at 1 and renumbers whenever the sort or filter changes.

## A package bought for someone else is that person's order

A customer buying for a friend is a real and repeated case: Maria for Fiana on 2026-07-07, Naya for Cila on 2026-08-24. Both went wrong, in opposite directions — Maria's conversation produced a duplicate phantom order on her own row, Naya's produced nothing at all for Cila. The rule is now one thing:

**The order sits on the person who eats the food. `orders.paid_by_customer_id` names the person who pays.**

The bot gathers the beneficiary's name *and* WhatsApp number and calls `extract_order` a second time with `beneficiary_name` / `beneficiary_phone`. `resolveBeneficiary()` normalises the number (`src/lib/utils/phone.ts`), finds that customer or creates one, and the order and all its delivery rows are written against them. If the number is missing or unreadable the bot asks for it and writes nothing — an order for a person we cannot identify by phone is an `IMPORT_` placeholder that will never match their next one. "Nggak tahu nomornya" is an escalation to an admin, not a reason to guess.

Operational consequences:

- **The quote goes to the buyer**, labelled `📦 Ini untuk pesanan atas nama <name>`. The beneficiary is never messaged — they never wrote to us, so there is no open 24-hour window, and they agreed to nothing.
- **The buyer's record is the only one ever updated.** Address, area and preferences from a chat belong to whoever is typing.
- **The package size on a beneficiary's order comes only from the model's extraction.** The transfer-amount match and the "20 porsi"/"sebulan" readings all describe a conversation covering two packages; applied to the friend's order they inflate it.
- **`/payments` shows a "Dibayar oleh" line** on any order with a payer, so a transfer under a name that does not match the order reads correctly instead of as a mismatch.
- **`cancel-unpaid` chases the payer.** Its notice goes to `paid_by_customer_id` when set.
- Two orders out of one conversation is now the correct outcome, not a duplicate. Before treating a `pending_payment` order as money owed, check `paid_by_customer_id` — the debt is the payer's, once.
- **The buyer's payment proof flips every order they are paying for, not only the one in their own name.** Both proof paths in the webhook — the image handler and the `mark_payment_proof_received` tool — used to match `.eq("customer_id", customerId)` alone, which is the beneficiary on a third-party order, so the friend's package stayed in `pending_payment` with nothing to show an admin that money had arrived. They now match `customer_id` **or** `paid_by_customer_id`. On 2026-08-30 Naya sent one transfer proof covering her own 20-porsi package and Cila's 5; only Naya's flipped, and `cancel-unpaid` was four hours from sweeping Cila's the evening before its 31 August start. Pinned by T14b in `test/webhook.test.ts`.
- **A beneficiary order created outside `extract_order` can arrive with `paid_by_customer_id` null**, and then nothing links it to the payer at all — not the proof handler, not `cancel-unpaid`'s notice, not the Payments page. Cila's was one: an `IMPORT_cila` customer row with no number and no payer. When entering a third-party order by hand, set the payer.

`linked_order_id` is a different thing entirely: use it when a person *draws from* someone else's package, never when they have their own order.

## Meal time preference types

These values are **display-only now**, and only on `customers.meal_time_preference` — a free-text column 381 of 384 customers leave null, rendered in one panel of the chatbot-training screen and read by no decision path. `orders.meal_time_preference` was dropped in migration 077, and the code that expanded these into dates was deleted on 2026-08-28. Never wire a new behaviour to them.

- `lunch_only`
- `dinner_only`
- `both_fixed` (e.g., 1 lunch + 1 dinner daily)
- `per_day_decision` (customer messages each day)
- `default_lunch` or `default_dinner` (default with ad-hoc overrides)
- `custom_schedule` (JSON with per-weekday preferences)
