# API Routes

Quick reference: which file handles which feature. Extracted from `CLAUDE.md` to keep root context lean — read this file on demand when working on API routes.

### Webhook (WhatsApp chatbot)
- `GET /api/webhook/whatsapp` — Meta webhook verification (hub.challenge handshake)
- `POST /api/webhook/whatsapp` — **Main chatbot entry point.** Inbound messages are written to `webhook_events` *before* the 200 is returned; if that write fails the route answers **503** so Meta retries rather than silently dropping the message, and the stored payload makes a failed processing run replayable (`processed_at is null` finds them). Status receipts skip this and are acknowledged straight away. Dedup via `processed_messages`, rate-limit check, Sonnet 5 conversation, tools: `extract_order` / `record_daily_order` / `escalate_to_human` / `ask_admin_for_help` — **every** `tool_use` block in the reply is executed, not just the last one, and `record_daily_order` takes `delivery_dates: string[]` so a multi-day schedule is one call (it skips dates already booked, never books past `portions_remaining`, and pushes a high-priority alert if the quota covered fewer days than promised). Meta `statuses[]` webhooks are also handled here and update the matching `conversations.message_id` row with `whatsapp_status` / `whatsapp_status_updated_at` (`sent`, `delivered`, `read`, `failed`). After each inbound customer message is saved to `conversations`, if Haiku's per-message intent classification returns `ordering` and the customer is not already in a current order lifecycle, `customer_state.state` is bumped to `ordering`. Payment-proof image handling and the "skip rate limit while waiting for proof" rule now key off the latest order status (`pending_payment`) instead of mirrored `customer_state` payment stages. Haiku auto-summarizes durable customer context via `src/lib/claude/learn-context.ts`, replaces the `[AI learned context]` block in `customers.notes`, and feeds the freshly learned notes into the same bot response when available; failures are logged and never block replying. Also handles welcome sequence: resolves `{{dapur_list}}`, `{{delivery_areas}}`, `{{price_20}}`, `{{order_deadline}}` placeholders in `welcome_message` setting from live DB data, then sends menu images from active subcontractor rows. After the T&C the welcome sequence sends one more bubble, `WINDOW_NOTICE_WELCOME` (`src/lib/whatsapp/window-notice.ts`), explaining WhatsApp's 24-hour window and asking the customer to message us first once it has passed; a send failure is logged and never blocks the rest of the flow. The welcome greeting + price list image + each menu image are also logged to `conversations` as `assistant` rows (`model_used: "system"`, image rows use `message_type: "image"` with the URL as content) so they render in the dashboard inbox. Before a reply is sent, `validateReply()` (`src/lib/claude/validate-reply.ts`, Haiku 4.5) checks it against the same "Current context" fields passed into `buildSystemPrompt` (name, notes, quota, state) and flags unsupported customer-specific claims — general FAQ/pricing/menu claims are never flagged. On rejection the bot regenerates once with a corrective instruction; if that also fails, the customer gets the `reply_validation_fallback` template instead of the raw reply, `customer_flags.pending_bot_response` is set, and admins get a high-priority push. The validator fails open (treats as valid) on any network/parse error so a validator outage never becomes a chatbot outage. Known gap: address and payment status aren't yet structured fields in `buildSystemPrompt`'s context, so the validator can't catch hallucinations on those two fields today.

### Orders
- `GET /api/orders` — List orders, optional `?status=` and `?search=` filters. Returns **all** matching rows: PostgREST caps one response at 1000, so the handler pages with `.range()` until a short page comes back. Never reintroduce a fixed `.limit()` here — a cap silently truncates the Orders table with no UI signal (this regressed twice: at 399 orders and again at 432).
- `POST /api/orders` — Admin creates a new order. One order shape for everything: a quota of portions. `delivery_schedule` is optional — when present the customer's days are already decided, so `package_size`, `start_date`, and `end_date` are derived from the array (never read off the body) and the `daily_deliveries` rows plus revenue/COGS journals for past dates are written here; when absent, `package_size` and `start_date` are required instead and delivery rows get written later as the customer asks for them. `meal_time_preference` is optional either way — a customer who decides day by day has no standing preference, and that absence is what downstream auto-expansion keys on. Also accepts `addon_cost_per_portion` (default `0`) — what the kitchen charges us extra per portion for an add-on such as nasi merah; cost side only, since the customer's share is already inside `price_per_portion`. It is added to the subcontractor's route rate by the COGS journal and by the `/dapur/[id]` bill. Also accepts `size` (`"s"` | `"m"`, default `"s"`) and `lunch_address_slot` / `dinner_address_slot` (`1` | `2`, default `1`) — a standing per-meal delivery-address rule (slot 2 = the customer's `address_2`). Persisted on the order; the `generate-deliveries` cron and the delivery rows written from a `delivery_schedule` stamp each `daily_deliveries` row's `address_slot` from the matching meal's slot. A per-day flip on the daily sheet still overrides.
- `PATCH /api/orders` — Requires `{ id, action }`. Actions: `"mark_paid"` (sets status → active, records conversion, posts journal + WhatsApp confirmation, and immediately pre-creates `daily_deliveries` for orders with a fixed meal preference instead of waiting for nightly cron; explicit `end_date` wins, otherwise weekday rows are generated from `start_date` until `package_size` portions are consumed; flexible prefs like `per_day_decision` / `custom_schedule` still skip auto-expansion here. Delivery upserts key on the table's real unique constraint: `delivery_date,customer_id,meal_type`; each row's `subcontractor_id` is the order's if set, otherwise the customer's — a null makes the delivery invisible on `/dapur/[id]`, which filters strictly on it). Payment/subscription truth now lives on `orders.status`; `customer_state` is no longer mirrored here. `"mark_payment_proof_received"` (manual admin transition from `pending_payment` → `payment_proof_received`; used by the Payments page's Awaiting payment tab when proof arrives outside the webhook flow). `"update_size"` (updates `size` column only, never recalculates price); `"update_fields"` (allowlisted operational columns only — `subcontractor_id, meal_time_preference, end_date, size, lunch_address_slot, dinner_address_slot, portions_lunch, portions_dinner, portions_per_delivery, addon_cost_per_portion, start_date`; area/address are customer-level and edited via the Customers page, not this endpoint; `addon_cost_per_portion` is the one money-adjacent field allowed here because it is cost-side only — what the kitchen charges us extra per portion, never what the customer paid — and it only affects COGS journals posted after the edit; never touches money/quota/status columns — `package_size`, `portions_remaining`, `price_per_portion`, `total_price`, `paid_at` are server-controlled and shown read-only in the detail slide-over, editable only via `mark_paid` or a future dedicated financial-correction action); `"update_status"` (safe side-effect-free transitions only — `paused`/`completed`/`cancelled_by_admin`, stamps `completed_at`/`cancelled_at`; rejects any other value incl. `active` so money-activation stays on the `mark_paid` path). The Orders table rows are clickable → a detail slide-over (`orders-client.tsx`) showing all order fields read-only, editing the operational set via `update_fields`, a Mark-Paid button (pending orders → `mark_paid`), and a status dropdown (→ `update_status`).
- `GET /api/orders/[id]/ledger` — Per-**order** draw ledger, derived on read: this order's `+package_size` credit followed by every `daily_deliveries` row whose `order_id` is this order, sorted by date with the credit before same-day draws and lunch before dinner. Returns `rows` (each with a running `balance`), `packageSize`, `totalDrawn`, `remaining` (computed from this order's own draws), `remainingToday` (draws dated today or earlier only), and `storedRemaining` (the `orders.portions_remaining` column, so the UI can flag drift). Deliberately narrower than the customer ledger at `GET /api/customers/[id]`, which sums every delivery a customer has regardless of which order it was charged to — that makes the customer view immune to misattribution and therefore blind to it. A delivery charged to the wrong package shows up here as a running balance going negative; it is invisible customer-side. Rendered in the Orders detail slide-over under "Draw history", with negative balances in red and a stored-vs-computed mismatch called out in amber.

### Customers
- `GET /api/customers` — List customers who have at least one paid order (status `payment_proof_received`/`active`/`paused`/`completed`); leads and unpaid/cancelled do not surface. `?all=true` returns every customer (used by the new-order modal so an admin can start the first order for a just-created, order-less customer) plus each customer's own `active_order_id` (their own active/paused order, if any — used to power the "draws from another customer" linking dropdown).
- `POST /api/customers` — Create a customer (e.g. someone who ordered a package manually via WhatsApp and isn't onboarded yet). Allowlisted fields only (`name, phone_number, area, sub_area, address, address_2, google_maps_link, subcontractor_id, linked_order_id`); `phone_number` and `address` (primary address) are required, `address_2` (secondary address) is optional; `phone_number` must be unique (duplicate → 409 with `existingId`). Used by the "+ Add customer" form on the Customers page and the inline "+ Buat pelanggan baru" creation in the new-order modal.
- `GET /api/customers/[id]` — Per-customer quota ledger, derived on read: every paid order (`active`/`paused`/`completed`/`payment_proof_received`) as a `+package_size` credit and every `daily_deliveries` row as a `−portions` draw, sorted by date with credits before same-day draws. Returns `rows`, `totalPackage`, `totalDrawn`, and **two** balances — `balanceToday` (draws dated today or earlier: what the customer has left right now, and the number to compare against `customers.portions_remaining` when chasing a mismatch) and `balance` (every draw including deliveries already scheduled ahead: what they will have once the current schedule runs out, and the number that says whether they need to top up). Package credits count in both, since quota is usable from the moment the order exists even if `start_date` is still ahead. Reads no stored counter, so it cannot drift.
- `PATCH /api/customers/[id]` — Update `name`, `notes`, or `linked_order_id` (allowlisted). Setting `linked_order_id` makes this customer's daily draws come from another customer's order instead of their own.
- `DELETE /api/customers/[id]` — Delete customer: detaches payment proofs, removes conversation state and rate limit records
- `PATCH /api/customers/reorder` — Bulk-update `delivery_position` for multiple customers; body: `{ updates: [{ id, delivery_position }] }`
- `POST /api/customers/free-quota` — Batch-grant free/goodwill portions (e.g. compensation for a late delivery). Requires `owner` or `admin` role. Body: `{ grants: [{ customer_id, portions, date, reason }] }`. Each grant inserts its own `orders` row (`source: "free_quota"`, `price_per_portion: 0`, `total_price: 0`, `package_size`/`portions_remaining`/`portions_per_delivery`: portions, `grant_reason`, `granted_by`: admin email) so it shows as a discrete `+N` "Kuota gratis" line in that customer's ledger, and bumps `customers.portions_remaining` by the same amount. No accounting journal is posted (Rp 0 double-entry would be degenerate). Writes one `edit_log` row (`action: "grant_free_quota"`) per batch. Used by the "+ Grant free quota" button/modal on the Customers page, which is an editable table — rows are added by hand or pasted from a spreadsheet, and Save is disabled until every row is complete, because the route validates the whole batch and rejects all of it if one grant is bad.

Conversion tracking columns on `customers` (migration 042): `ad_creative` (e.g. `"C4"`, auto-detected from first WhatsApp message), `first_message`, `converted_at` (set on first `mark_paid`), `package`, `total_portions`, `total_payment`, `promo_used` (manual), `converted_to_subscription` (boolean), `notes`. All editable via the customer detail panel.

Second address columns on `customers` (migration 044): `address_2`, `area_2`, `sub_area_2`, `google_maps_link_2`. Linked to `daily_deliveries.address_slot` (1 = primary, 2 = secondary, default 1).

Standing per-meal address rule on `orders` (migration 048): `lunch_address_slot`, `dinner_address_slot` (`smallint`, `IN (1, 2)`, default 1). Set in the new-order modal (toggles shown only when the customer has `address_2`). The `generate-deliveries` cron stamps each generated `daily_deliveries` row's `address_slot` from the matching meal's order slot, and scheduled orders stamp their rows at creation. A per-day flip on the daily sheet still overrides for a single day.

### Deliveries
- `GET /api/deliveries/daily-sheet` — Fetch delivery rows for a given date
- `POST /api/deliveries/daily-sheet` — Create daily delivery rows for a date. Groups the fixed-schedule active orders by customer and runs each group through `pickDrawOrder` (see "Which order a delivery draws from" in CLAUDE.md) so a customer holding two standing orders gets one row per meal, charged to a chosen order rather than to whichever the upsert happened to keep.
- `PUT /api/deliveries/daily-sheet` — Save edited rows for a date (upsert `daily_deliveries`, post revenue/COGS journals per non-skipped row; quota deduction handled by the nightly cron). Every row links an `order_id` (a draw always comes from a package) — **enforced**: any non-cancel row without one rejects the entire save with 400 and names the customers involved, so the admin creates the order first. Before the guard, an unlinked row saved fine but silently skipped both the order deduction and the revenue/COGS journal; 21 such rows reached production (backfilled 2026-08-13).
- `GET /api/deliveries/addable-customers` — List customers Agnes can manually add to a daily sheet (a customer who decided to draw extra from their package for a date but has no auto-generated row). A draw always comes from a package — customers cannot buy a fresh one-off — so only customers with an active recurring order **(own, or resolved via `customers.linked_order_id` to someone else's)** are returned, each with the address/route fields the sheet renders plus their `active_order`. When a customer holds several active orders, `active_order` is chosen by `pickDrawOrder` — oldest package that still has balance — not by whichever row Postgres returned first. The Deliveries → Daily Sheet tab has an "Add customer" button → modal (searchable customer combobox, meal type, portions, dapur) that appends a `daily_deliveries` row (linked to the active order's `order_id`) to local state; admin clicks Save to persist (nightly cron deducts quota, save posts journals).
- `POST /api/deliveries/bulk-create` — Write several `daily_deliveries` rows for one customer at once. Requires the customer to have a subcontractor and at least one active order; the order charged is chosen by `pickDrawOrder`.
- `GET /api/deliveries/proofs` — List payment proof photos with signed URLs
- `POST /api/deliveries/proofs` — Upload proof photo (admin upload); stamps `received_at` to the admin-selected delivery date so it lands on the right day, inserts with `status: "admin_uploaded"` and `matched_customer_id`; surfaces in the "Ready to send" section of the Proof of Delivery tab.

### Inbox (admin-guided bot responses)
- Dashboard inbox thread list supports three client-side filters: `All`, `Unread`, and `Unanswered`. `Unread` means the latest conversation row is a customer (`role: "user"`) message; `Unanswered` means `customer_flags.pending_bot_response = true` or `customer_flags.escalated_to_human = true`. A search box further filters visible threads by customer name, phone number, or last message content, client-side, combined with the tab filter.
- Assistant/inbox outbound rows persist Meta's returned `message_id` and start at `whatsapp_status = "sent"` so the UI can later show `Sent`, `Delivered`, or `Read` from webhook updates.
- Manual text replies, manual image sends, manual PDF sends, and human takeover all clear `customer_flags.pending_bot_response`, so a thread doesn't stay stuck "awaiting bot reply" after an admin handles it.
- `POST /api/inbox/manual-reply` — Admin sends a hand-typed text message to a customer from the inbox composer. **Owner-only: 403 for role `admin`.** Sends via WhatsApp, then logs an `assistant` row (`model_used: "human"`) so the send appears in the thread.
- `POST /api/inbox/manual-image` — Same, for an image. Compresses the upload, pushes the bytes to Meta with `uploadMediaToMeta`, sends by id, logs an `image` row. **Owner-only.**
- `POST /api/inbox/manual-document` — **Owner-only (403 for role `admin`).** Admin sends a PDF to a customer from the inbox composer (📎 button accepts `image/*,application/pdf`; Cmd+V paste of a PDF also works). Multipart body: `customer_id`, `file`, optional `caption`. Rejects anything that isn't `application/pdf` or is over 100MB (Meta's document cap). Uploads the raw PDF to the `menu-images` bucket under `inbox/{customer_id}/{ts}-{filename}` for history display, uploads the same bytes to Meta's media endpoint, sends via `sendDocumentMessageById` (`type: "document"`, original filename preserved), then logs an `assistant` row with `message_type: "document"` and the public URL as content. No compression — PDFs are sent byte-for-byte.
- Inbound customer PDFs (`type: "document"` webhook messages) are saved to `conversations` with `message_type: "document"`, `media_id` = Meta's document id, and content `[Dokumen: filename]`. The bot does not read PDFs — it replies with the `text_only` template and the document shows in the inbox as a clickable link served through `GET /api/inbox/media/[mediaId]` (that proxy already passes Meta's `mime_type` through, so PDFs render inline). Payment proofs sent as PDF are **not** routed to the payment-proof handler, which is image-only.
- `POST /api/inbox/bot-reply` — Admin provides a concise answer → Haiku polishes it → bot sends polished message to customer → clears `pending_bot_response` flag. Optional `save_as_rule: true` also rephrases the answer into a general instruction and inserts it into `chatbot_instructions` so future customers get it automatically (opt-in checkbox in the inbox UI).
- `GET /api/inbox/delivery-proofs/[...path]` — Auth-gated proxy for proof images stored in Supabase Storage; used by the inbox UI so proof attachments render without exposing the storage bucket directly.
- `GET /api/inbox/chat-media/[...path]` — Auth-gated proxy for inbound WhatsApp media saved into the private `chat-media` bucket, signing the object path per request. Mirrors the delivery-proofs proxy. Media lands in that bucket two ways: the webhook stores it at receipt time and records `conversations.media_url`, and `scripts/backfill-chat-media.ts` rescued older rows by writing the URL into `conversations.content`.
- `POST /api/inbox/learn-context` — Manual fallback for the same learned-context summarizer used by the webhook auto-learn path. Requires admin auth and `{ customer_id }`; writes only the `[AI learned context]` block in `customers.notes`.
- `POST /api/inbox/pipeline-stage` — Admin override for customer-level funnel/lifecycle state only. Updates `customer_state.state` to slim states (`new`, `ordering`, `lapsed`, `churned`; legacy `"browsing"` input is normalized to `new`). Payment/subscription state changes no longer happen here and must go through `orders.status`.
- `POST /api/inbox/replay-latest` — Re-run the latest saved inbound customer text through the normal chatbot flow. Requires auth and `{ customer_id }`. Refuses only on `is_blacklisted`, or when the latest message is not usable (`latest_not_user`, `latest_not_text`, `empty_message`). It does **not** refuse on `escalated_to_human` / `pending_bot_response` — it selects both columns but never checks them. An earlier `thread_blocked` guard is gone, which is why the old "Regenerate reply" cleared those flags before replaying: it was working around a refusal that no longer happens. Pass `{ draft: true }` for **draft mode**: the reply is generated and returned as `{ ok: true, replayed: true, draft: "..." }` and **nothing else happens** — no WhatsApp send, no `conversations` row, no tools, no rate-limit charge, no `analyzeCustomerMessage`. An empty generation returns `reason: "empty_draft"`. Draft mode calls the model **without tools** on purpose: every tool on this path (`create_order`, `send_menu_image`) does something the customer sees or the books record, and a draft the admin then discards must leave nothing behind. Without tools the model always answers in text, which is what the compose box needs.
- **"Draft bot reply"** (inbox thread header → More menu) — writes the bot's suggested reply into the compose box for the admin to edit and Send. Calls `replay-latest` with `{ draft: true }` and sends nothing itself. It deliberately does **not** clear `escalated_to_human`: drafting on a thread you took over must not hand it back to the bot. This button used to send its reply straight to the customer with no preview, under the label "Regenerate reply" and a status line ("Analisis dikirim ke halaman Assistant.") that described neither what it did nor where the output went.
- `POST /api/inbox/takeover` — Sets or clears `customer_flags.escalated_to_human` (plus `escalation_reason`, `last_human_activity_at`, and clearing `pending_bot_response`). **`escalated: true` is owner-only — 403 for role `admin`.** Takeover silences the bot for that customer and quietly transfers everything it would have done unprompted, delivery-row generation most of all, onto whoever took over; that is how Jordy's package lost three of its five days. `escalated: false` is allowed for any signed-in admin, because handing the thread back to the bot is the safe direction and `resumeBot` in the inbox calls it. The "Take over" button is hidden for non-owners; "Resume bot" still renders for them on a thread already in takeover. The three `manual-*` send routes are owner-only for the same reason, and the compose box is gated on the viewer being an owner *and* the thread being in takeover — admins message customers through the Assistant's `send_whatsapp_message` / `send_whatsapp_image` instead, which is auth-only and open to every role.
- **"Resume bot"** (amber "Bot paused" banner) — the one that still sends. Clears `escalated_to_human` / `pending_bot_response` via `POST /api/inbox/takeover` with `{ escalated: false }`, then calls `replay-latest` **without** `draft`, so the bot answers the waiting customer for real. Shows the `reason` inline if the replay doesn't fire (e.g. `welcome_flow_only`, `latest_not_user`).
- `POST /api/inbox/extract-order` — Admin-triggered manual order extraction, for when the bot got stuck (rate-limited, escalated, errored) before ever calling its own `extract_order` tool — common when a customer already typed their full order into chat but the bot never reached the confirmation step. Re-runs Sonnet against a deeper slice of the customer's saved conversation history (60 messages, not just the most recent 20) with `tool_choice` forced onto the `extract_order` schema, trims any trailing assistant messages first because Anthropic forced tool-use requires the conversation to end on a user turn, and also includes any saved `[AI learned context]` notes in the system prompt so the model can still recover fields like area or clarified dates after later back-and-forth. Returns the parsed fields plus server-computed `price_per_portion` and `total_price` for the review modal, without writing to the DB. Shares its DB-write logic (`createOrderFromExtraction` in `src/lib/claude/extract-order.ts`) with the bot's own live `extract_order` tool handler in the webhook route, so the two paths can't drift apart. The live bot's automatic extraction during a real conversation is unaffected — this is purely an additional manual escape hatch. The forced Anthropic tool-use call is wrapped in try/catch (logs and returns `null` → 422 "Could not extract order details from this conversation") so an Anthropic API error surfaces as a real JSON error instead of an unhandled exception that the client can't parse.
- `POST /api/inbox/extract-order` — Admin-triggered manual order extraction, for when the bot got stuck (rate-limited, escalated, errored) before ever calling its own `extract_order` tool — common when a customer already typed their full order into chat but the bot never reached the confirmation step. Re-runs Sonnet against a deeper slice of the customer's saved conversation history (60 messages, not just the most recent 20) with `tool_choice` forced onto the `extract_order` schema, trims any trailing assistant messages first because Anthropic forced tool-use requires the conversation to end on a user turn, and also includes any saved `[AI learned context]` notes in the system prompt so the model can still recover fields like area or clarified dates after later back-and-forth. After extraction, the server normalizes `package_size` from the conversation text when the chat explicitly states total portions (for example `2 porsi x 5 hari = 10 porsi`), so pricing in the review modal uses total portions rather than day-count or per-delivery portions. Returns the parsed fields plus server-computed `price_per_portion` and `total_price` for the review modal, without writing to the DB. Shares its DB-write logic (`createOrderFromExtraction` in `src/lib/claude/extract-order.ts`) with the bot's own live `extract_order` tool handler in the webhook route, so the two paths can't drift apart. The live bot's automatic extraction during a real conversation is unaffected — this is purely an additional manual escape hatch. The forced Anthropic tool-use call is wrapped in try/catch (logs and returns `null` → 422 "Could not extract order details from this conversation") so an Anthropic API error surfaces as a real JSON error instead of an unhandled exception that the client can't parse.
- `POST /api/inbox/extract-order/pricing` — Authenticated admin helper used by the inbox review modal when `package_size` is manually corrected after extraction. Returns server-computed `price_per_portion` and `total_price` for the supplied `package_size`; confirm/create still recomputes pricing server-side and does not trust client money fields.
- `POST /api/inbox/extract-order/confirm` — Admin confirms the (optionally edited) parsed fields from the review modal. Accepts optional `send_payment_info` (default `true`): when `true`, creates the order (`pending_payment`) and sends the payment-details WhatsApp message; when `false`, creates the order only and skips the outbound payment message. The live bot path still uses the same shared helper with the default send behavior.
- "Extract order" (inbox thread header → More menu) — opens a review modal (name, address, maps link, area, package size, portions/delivery, start/end date) pre-filled from the extraction call; admin edits anything wrong, then confirms to create the order.

### Settings
- `GET /api/settings` — All settings + pricing tiers + message templates + admin list
- `PATCH /api/settings` — Update a single settings key (e.g. `{ key: "order_deadline_hour", value: "20" }`)
- `POST /api/settings/admins` — Add admin user + create Supabase Auth account; body: `{ email, role? }` (`role` defaults to `"admin"`)
- `PATCH /api/settings/admins` — Change an existing admin's role; body: `{ email, role }` (`"owner"` or `"admin"`); audit-logged
- `DELETE /api/settings/admins` — Remove admin user and their Supabase Auth account
- `POST /api/settings/menu-image` — Upload price list image (`price_list_image_url` only; dapur menu images are managed per subcontractor)
- `PATCH /api/settings/pricing` — Update a single pricing tier, or bulk-adjust all tiers with `{ adjust: number }`
- `PATCH /api/settings/templates` — Update a message template by key

### Subcontractors
- `GET /api/subcontractors` — List all subcontractors with off days
- `POST /api/subcontractors` — Create a new subcontractor
- `PATCH /api/subcontractors/[id]` — Update allowlisted fields (name, nickname, phone, areas, notes, cost, menu_text, menu_week_start, etc.). `menu_week_start` must be `YYYY-MM-DD` or null (400 otherwise).
- `POST /api/subcontractors/[id]/menu-image` — Upload menu image to `menu-images` bucket → save URL to subcontractor row, plus `menu_week_start` (the Monday the image covers). Accepts an optional `menu_week_start` form field; otherwise defaults from the upload day via `defaultMenuWeekStart()`. Returns it in the JSON so the form can show it back for correction.
- `GET /api/subcontractors/[id]/daily-sheet` — **Dapur Sheet** API: public (no auth), returns tomorrow's `daily_deliveries` for this subcontractor with lunch/dinner × rute1/rute2 summary. Supports `?date=YYYY-MM-DD`. Respects `address_slot` so slot-2 customers show their secondary address.
- `POST /api/subcontractors/off-days` — Add an off day for a subcontractor
- `DELETE /api/subcontractors/off-days` — Remove an off day

### Dapur Sheet
A public, auth-free mobile page at `/dapur/[subcontractor-uuid]` shared with each subcontractor so they can see tomorrow's delivery orders without a dashboard login. Shows a lunch/dinner × Rute 1 (diantar Pian Yi) / Rute 2 (diantar subcontractor) portion summary, then per-order cards with name, area, sub_area, address (slot-aware), Maps link, notes, and portions. Two note lines are rendered and they come from different tables: "Catatan" is `daily_deliveries.notes` (that day's instruction) and "Preferensi" is `customers.notes` (standing dietary/drop-off preference). Because the page is auth-free, `customers.notes` goes through `kitchenPreferences()` first. It prefers the manually typed notes with the `[AI learned context]` block stripped; only when a customer has no manual notes at all does it fall back to `aiPreferences()`, which pulls the `Preferensi*` bullets out of the AI block and nothing else — the sibling labels (`Catatan`, `Pesanan`, `Area layanan`) hold order cutoffs, bank details, and price points a subcontractor has no reason to see. Four filters drop what survives that: `MEAL_ONLY` (a clause that is nothing but "makan siang saja" — the card already sits under the MAKAN SIANG heading; anchored at both ends so "siang ayam-malam daging" survives), `MONEY` (the model sometimes writes prices into a `Preferensi` bullet anyway), `COMPARISON` (a preference can record that the customer is shopping around — true, but not for the kitchen being compared against), and `ORDERING_MODEL` (the model files our own package mechanics under "Preferensi": "sistem fleksibel, porsi bisa dipakai kapan saja" describes how we sell, not how to cook). Each is deliberately narrow: `COMPARISON` matches comparison intent rather than the bare word "dapur" so "perlu konfirmasi ke dapur" survives, and `ORDERING_MODEL` excludes "per porsi" and "paket" because those appear in real food notes like "nasi + 3 lauk per porsi". Filtering runs **per clause**, not per bullet — one line routinely mixes both kinds ("Makan siang saja, porsi kecil, sistem fleksibel …" keeps the first two and drops the third) — and `balanceParens()` cleans up a parenthesis whose other half was in a dropped clause. Against production: 46 manual / 15 extracted / 11 blank. Supports `?date=YYYY-MM-DD` for non-default dates. Thenie's link: `/dapur/52cd5e62-da09-49c9-939c-2f1246566c40`.

### Admin Assistant
- `POST /api/assistant` — Multi-turn agentic chat using Sonnet 5. Runs tool loop (max 10 turns) with read tools: `query_customers`, `query_orders`, `query_deliveries`, `query_financials`, `query_metrics`, `search_conversations`, `query_menu_assets`. Write tools (`mark_order_paid`, `cancel_order`, `send_whatsapp_message`, `send_whatsapp_image`, `update_customer_field`) are intercepted — returns `{ ok: true, text, pendingAction }` instead of executing. If Claude proposes multiple WhatsApp send actions in one response (for example menu image + price list image), the route returns one `pendingAction` with `tool: "batch"` and an `actions` array so the admin confirms once and every send is preserved. If the loop ends without an answer — turns exhausted, or a `stop_reason` it cannot continue from such as `max_tokens` — the route makes one final call with the tools removed, so the model must answer from the lookups already in context. Turn budget was 5 and the wrap-up did not exist: a compound request ("Julian wants to renew, and add 1 portion for tomorrow") measured at exactly 5 turns of read-tool fan-out, and anything needing a sixth returned the generic "I couldn't generate a response" string. The old salvage path could never have caught it either — it looked for text on the last message, which on turn exhaustion is always the tool_results `user` turn. Every path that still reaches the generic string now `console.error`s the stop_reason and turn count first; before, the route logged nothing at all. Body accepts optional `conversationId`; if absent, a new thread is created lazily and returned. Each turn (user msg + reply) is persisted to `assistant_conversations` / `assistant_messages` (shared across all admins). Requires auth.
- `POST /api/assistant/stream` — **Streaming twin of `POST /api/assistant`, and what the dashboard actually calls.** Same agentic loop, same write-tool interception, but emits Server-Sent Events as the work happens: `conversation` (the lazily created thread id), `text` (token deltas), `step` / `step_done` (one tool call each, labelled by `describeToolCall` and summarized by `summarizeToolResult` in `src/lib/claude/assistant-steps.ts` — the summary is a row count, never the payload, which runs to tens of KB), `pending_action`, `error`, `done`. Turn budget is 25, not the non-streaming route's 10: the cap only ever existed because the admin stared at a blank spinner and browsers/proxies time out silently, and both stop being true once the answer paints as it arrives and a Stop button aborts it. `request.signal` is threaded into every model call, and an abort is treated as the admin pressing Stop — whatever text already streamed is still persisted, not discarded. Sets `X-Accel-Buffering: no` and `Cache-Control: no-transform` so Railway's proxy can't buffer the stream into one lump, which would look identical to the spinner this replaces. The non-streaming route is unchanged but now has **no in-app caller** — the dashboard was its only one. It is kept as the single-JSON-blob entry point (and its `test/api/assistant.test.ts` suite still covers it); delete it only after confirming nothing external posts to it.
- `POST /api/assistant/execute` — Execute a confirmed write-tool action. Body: `{ tool, input, conversationId? }`. Accepts tools in `WRITE_TOOLS` plus `tool: "batch"` for multiple confirmed WhatsApp sends. `mark_order_paid` side effects: sets status → active, conversion tracking, journal entry (Dr Bank BCA / Cr Uang Muka), immediate fixed-recurring `daily_deliveries` pre-generation (same rules as `PATCH /api/orders mark_paid`), WhatsApp confirmation to customer. Payment/subscription truth now stays on `orders.status` and is not mirrored into `customer_state`. `send_whatsapp_message` sends text via WhatsApp, then looks up the customer by `phone_number` and logs the message to `conversations` as an `assistant` row (`model_used: "human"`) so it appears in the dashboard inbox. `send_whatsapp_image` downloads the public image URL, uploads the binary to Meta with `uploadMediaToMeta`, sends by `sendImageMessageById` (not by `image.link`, which can fail silently), then logs the public URL to `conversations` as an `assistant` image row (`message_type: "image"`, `model_used: "human"`). `create_order` sets the new order's `subcontractor_id` from the customer (this path has no admin form to take one from, and a null propagated into every generated delivery row, hiding them from the kitchen's page). It also rejects a `portions_per_delivery` that is below 1 or above `package_size`: it is one day's portions, never the package total, and a model that confuses the two makes every generated delivery draw the whole package. That is not hypothetical — Julian S's 17 Agustus renewal was created with package 5 / per-delivery 5, and `buildRecurringDeliveryRows` duly wrote four days at 5 portions each. The confirmation card now also prints `Per pengiriman` and the end date; it previously showed neither, so the wrong number was never on screen for the admin to catch. If Meta refuses a send because the customer's 24-hour service window has closed (error `131047`, or legacy `470`), the route answers **409** with `code: "window_closed"` and an Indonesian explanation naming the number, instead of letting the throw become a 500 carrying a raw Meta payload. Nothing we send reopens the window — only an inbound message from the customer does — so the admin needs to read this as "they have to write first", not "the app is broken". It matters more now that hand-typed sends are owner-only and this is the admin's only route to a customer. In a `batch`, the first refused action returns and the remaining ones are not attempted. `update_customer_field` allowlist: name, address, area, notes. `update_order` allowlist: meal_time_preference, portions_per_delivery, portions_lunch, portions_dinner, start_date, end_date. Both allowlists are typed as `Extract<keyof …["Update"], …>` over the generated table types, so a name that is not a real updatable column fails typecheck rather than silently never matching. Confirmation reply persisted to the thread when `conversationId` is provided. Requires auth.
- `POST /api/assistant/daily-brief` — Claims the once-a-day automatic morning briefing. Returns `{ ok: true, claimed: boolean }`; the assistant UI sends the briefing prompt only when `claimed` is true. The claim is an `insert` into `assistant_daily_briefs` keyed on the Jakarta date — the unique violation *is* the guard, so two devices opening the assistant at the same moment produce exactly one winner. The check used to be `localStorage`, which is per-browser and so fired again on every new device. Any error, including a DB outage, is treated as "not claimed" (fail closed): a missing briefing is a smaller annoyance than a duplicate one. Requires auth.

### Accounting
- `GET /api/accounting` — Paginated journal entries with optional date range filter
- `POST /api/accounting` — Owner-only. Create a manual balanced journal entry. Body: `{ date (YYYY-MM-DD), description, lines: [{ accountCode, debit, credit }] }`. Validates each line is debit XOR credit, total debit = total credit (> 0), and every `accountCode` exists. Inserts a `journals` header (`source_type: "manual"`, `source_id: null`) with an atomic `next_journal_reference` reference, then `journal_lines`; rolls back the header if line insert fails.
- `GET /api/accounting/accounts` — Owner-only. Active chart of accounts (`code, name, type`) for the manual-journal form dropdown. With `?all=true` returns every account incl. inactive with full fields (`id, code, name, type, normal_balance, category, is_active`) for the Akun management tab.
- `POST /api/accounting/accounts` — Owner-only. Create a chart-of-accounts entry. Body: `{ code (3–5 digits, unique), name, type (Asset|Liability|Equity|Revenue|Expense), category }`. `normal_balance` is derived server-side (Asset/Expense → Debit, else Credit), never accepted from client. Rejects duplicate code.
- `PATCH /api/accounting/accounts/[id]` — Owner-only. Edit `name`, `category`, or toggle `is_active`. `code`/`type`/`normal_balance` are immutable once created (locked to protect historical postings). Accounts are never deleted (referenced by `journal_lines`); deactivate hides them from the journal dropdown.
- `GET /api/accounting/reports?type=&from=&to=` — Owner-only. Server-computed financial statements from `journal_lines`. `type=trial_balance` (each account netted onto its normal side, `from` optional, cumulative through `to`); `type=pnl` (revenue − expense over `from..to`, returns `netIncome`); `type=balance_sheet` (assets / liabilities / equity cumulative through `to`, with cumulative revenue−expense folded into equity as a "Laba ditahan & berjalan" line, plus `balanced` flag).
- `GET /api/accounting/ledger?account=<code>&from=&to=` — Owner-only. Per-account general ledger: opening balance (net of lines before `from`), every line in range with a running balance on the account's normal side, and closing balance.

### Health
- `GET /api/health` — **Liveness** probe (returns 200 OK). Touches nothing, deliberately: this is Railway's `healthcheckPath`, and a deploy-time check that fails on a vendor outage would roll back a perfectly good release. Do not add a database query here.
- `GET /api/health/db` — **Readiness** probe. Reads one row from `settings`; 200 `{ ok, latencyMs }` when PostgREST answers, 503 `{ ok: false, error, latencyMs }` when it does not. **This is the endpoint an uptime monitor should watch.** It exists because `/api/health` stayed green through the entire 2026-08-18 Supabase REST outage while every dashboard page hung on a spinner — a health check that cannot fail cannot page anyone.

### Cron (all require `CRON_SECRET` header)
Triggered by the in-app scheduler (`src/lib/cron/scheduler.ts`, started from `src/instrumentation.ts`, enabled by `CRON_IN_APP=true`), which calls each route handler in-process with the secret header. They stay ordinary HTTP routes, so any of them can still be run by hand with curl. `generate-deliveries` is the exception — it is in no schedule and only runs manually.

- `GET /api/cron/auto-resume-bot` — Resume chatbot for escalated customers whose admin has been inactive longer than `TAKEOVER_INACTIVITY_MINUTES` (30, from `src/lib/customers/takeover.ts`), read off `last_human_activity_at`. Learns customer context first, then clears `escalated_to_human`, `escalation_reason`, and `last_human_activity_at`, then **replays the customer's latest message** through `replayLatestCustomerMessage` so a question that arrived during the takeover actually gets answered. The replay is a no-op unless the newest message is still an unanswered customer text, so a thread the admin already replied to stays quiet; a replay failure is logged and does not undo the resume. Rows with a NULL `last_human_activity_at` are never resumed — there is no clock on them, so they stay with the human. This sweep is the backstop for threads whose customer never writes again; the webhook resumes inline (see below) when they do. Capped at 10 customers per run (each costs up to two Claude calls — context learning, then the replayed reply); leftovers roll to the next tick. Runs every 15 min.
- `GET /api/cron/abandoned-recovery` — Re-message customers stuck in ordering state with no completed order (hourly)
- `POST /api/cron/cancel-unpaid` — Cancel orders that remain unpaid after N hours; notify customer (hourly)
- `POST /api/cron/daily-summary` — Push notification with yesterday's metrics (09:00 WIB)
- `POST /api/cron/deduct-daily-quota` — Draw one portion per delivered meal off each quota order's `portions_remaining` (21:00 WIB)
- `GET /api/cron/generate-deliveries` — Pre-create `daily_deliveries` rows for tomorrow (manual only — on no schedule). Same per-customer `pickDrawOrder` grouping as the daily sheet's Generate.
- `GET /api/cron/lapsed-customers` — Detect customers who haven't ordered recently; send re-engagement message (10:00 WIB)
- `GET /api/cron/post-delivery-followup` — Send satisfaction follow-up WhatsApp message after delivery (15:00 WIB)
- `GET /api/cron/refresh-wa-window` — Keep the 24-hour WhatsApp service window open on active threads (08:00 and 20:00 WIB). If the window lapses before the send lands (Meta 131047), falls back to the approved `jendela_24_jam` template
- `GET /api/cron/renewal-reminders` — Warn quota customers whose balance is running low (hourly)
- `POST /api/cron/send-reminders` — Send payment reminder to customers with unpaid orders (every 2 hours)
